# Workflow 定义 — 双 Agent 协作流程规范

> 位置：~/.claude/global-memory/templates/WORKFLOW.md
> 用途：定义任务从启动到完成的阶段流转、交接物、打回条件
> 核心原则："发现问题的人不能自己修"——审查和执行角色分离

---

## 一、单 Agent 工作流（大多数日常任务）

适用场景：单一 Agent 即可完成的任务（学习、Bug 修复、文档生成等）

```
┌─────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  SPEC    │───>│  执行    │───>│  自检    │───>│  验证    │───>│  交付    │
│  定义    │    │  Agent工作│    │  Agent自查│    │  脚本验证 │    │  + 记忆  │
└─────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
     │              │               │               │               │
   你填写        Agent执行      Agent对照SPEC     verify_all.py    更新记忆
                                 逐条自查          硬性判定        写入Git
```

### 各阶段定义

| 阶段 | 谁做 | 输入 | 输出 | 打回条件 |
|------|------|------|------|---------|
| SPEC 定义 | 你 | 需求/想法 | 填好的 SPEC.md | — |
| 执行 | Agent | SPEC + 相关文件 | 交付物 | — |
| 自检 | Agent | SPEC 完成标准 | 自检报告（逐条 Yes/No） | 有 No → 回到执行 |
| 验证 | 脚本 | 交付物 | verify 报告 | Error → 必须修复；Warning → 告知 |
| 交付 | 你+Agent | 通过验证的产物 | 最终产物 + 记忆更新 | — |

### 关键规则

1. **SPEC 前置**：满足以下**任一条件**时必须先填 SPEC：
   - 预估 >5 轮 **且** 涉及新文件创建或架构变更
   - 用户明确要求写 SPEC
   其他情况下，一句话需求描述即可开始。
2. **自检不可跳过**：Agent 完成后必须对照 SPEC 完成标准逐条自查
3. **脚本验证是硬门禁**：Error 级别必须修复后才能标记完成
4. **记忆写入是收尾动作**：任务完成后检查是否触发记忆写入

## 二、双 Agent 协作流程（复杂任务）

适用场景：需要学习 Agent 和工作 Agent 接力的任务（如先学习新技术再落地实现）

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  SPEC    │───>│ 学习Agent │───>│  Handoff │───>│ 工作Agent │───>│  验证    │
│  定义    │    │  研究阶段 │    │  交接    │    │  执行阶段 │    │  + 交付  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
```

### 交接物（Handoff）格式

```markdown
# Handoff: [任务名称]

## 交接日期：[YYYY-MM-DD]
## 从：学习 Agent → 到：工作 Agent

## 研究结论摘要
- [3-5 条核心发现]

## 推荐方案
- [方案描述]
- [为什么选这个]

## 注意事项
- [踩坑点]
- [约束条件]

## 相关文件
- [路径列表]

## 工作 Agent 需要做什么
- [ ] [具体任务 1]
- [ ] [具体任务 2]
```

### 打回机制

| 场景 | 谁发现 | 怎么处理 |
|------|--------|---------|
| 工作 Agent 发现研究结论有误 | 工作 Agent | **不自己改结论**，生成打回报告，回到学习 Agent |
| 验证脚本发现代码问题 | 脚本 | 回到工作 Agent 修复 |
| 你发现方向偏了 | 你 | 更新 SPEC，从偏离点重新开始 |

## 二-B、跨模块重构流程（补充）

适用场景：修改涉及 3+ 个文件、可能破坏编译的重构任务

### 增量提交策略
1. 重构前创建 WIP 分支
2. 每修改一个模块完成后，确保该模块**单独可编译**再继续
3. 每个可编译的中间状态做一次 commit（message: `wip(scope): 描述`）
4. 全部完成后 squash 为一个正式 commit

### 回退策略
- 如果某步修改导致连锁编译错误且超过 3 轮未修复 → `git stash` 回退到上一个 WIP commit
- 不要试图在编译错误的基础上继续修改其他文件

## 三、Skill 介入规则

在任何工作流阶段，如果匹配到已有 Skill，优先使用 Skill：

| 任务类型 | 对应 Skill | 触发时机 | 触发门槛 |
|---------|-----------|---------|---------|
| Bug 排查 | bug-locator | 执行阶段，问题定位时 | 复现+定位超 2 轮未解决 |
| 代码/文档审查 | skill-reviewer | 自检阶段 | 用户要求 review 或 >100 行 |
| 代码搬迁 | migrate-executor | 执行阶段，涉及模块迁移时 | 3+ 文件的模块级迁移 |
| C++ 概念学习 | cpp-tutor | 学习 Agent 研究阶段 | 进入 C++ 学习话题 |
| Skill 创建/更新 | skill-creator | 有新工作流需要固化时 | 重复 3+ 次的稳定流程 |

## 四、上下文管理规则

| 对话轮数 | 动作 |
|:--------:|------|
| 开始 | 读取 MEMORY.md 索引 + 相关 Topic 文件 + 项目 dev-map |
| 第 10 轮 | Agent 主动轻提醒："已 10 轮，是否需要 compact？" |
| 第 15 轮 | 强烈建议 compact 或拆对话 |
| 任务切换 | 先 compact 当前任务 → 写 handoff → 新对话 |
| 对话结束 | 检查记忆写入触发条件 → 直接执行写入 |

## 五、从工作流到 Skill 的下沉判断

如果某个工作流模式被重复使用 3+ 次，考虑下沉：

```
重复的工作流片段
    ↓ (3+ 次使用)
提取为 Skill（SKILL.md + examples/）
    ↓ (某步骤逻辑完全固定)
抽取为 Script（零 token）
```

下沉前问自己：
1. **这是通用问题还是特殊场景？** → 只有通用问题才下沉
2. **下沉后会不会过拟合到当前项目？** → 确保模板化
3. **有没有 3 个以上不同的使用场景？** → 至少能想到 3 个才值得
