# ADR-004 · 中文人类向 + 英文 AI 派生

- **状态**:Accepted
- **创建**:2026-04-24
- **关联 Phase**:0(文件名约定迁移)
- **关联横切原则**:DESIGN §1.4 第 4 条

## 背景

任务目录里两类文档混在同一文件树:**人类参与讨论的**(REQUIREMENTS / DESIGN)和 **AI 派生的**(SPEC / HANDOFF / WORKFLOW / HARNESS_REVIEW)。当前全用大写英文命名,扫一眼分不清"哪些要我亲自审"和"哪些是 AI 自动生成的派生品",导致:

- 用户打开任务目录后要逐个文件读才知道该不该编辑
- AI 在 Step 4 收尾时容易写到不该写的文件
- `style-refs/` 里的样例(`【需求分析】XX.md`)已经是中文,反例是任务目录全英文

## 候选方案

### A. 全英文(现状)

**优**:工具链统一(grep / git 跨仓库一致);简单。
**劣**:视觉无区分;新人/AI 都要靠记忆判断"这个该不该编辑"。

### B. 全中文

**优**:文件树视觉清爽。
**劣**:派生文档(SPEC/HANDOFF)是 AI 主要操作对象,改名后所有 hook/script 引用都要重写,迁移成本极高,收益不对称。

### C. 中文人类向 + 英文 AI 派生(本 ADR 选定)

人类参与的文档(讨论/审阅)用中文文件名;AI 自动派生的产物保持英文。

| 类型 | 受众 | 文件名 |
|---|---|---|
| 需求分析 | 人 + AI 共写 | `需求分析.md` |
| 设计文档 | 人 + AI 共写 | `设计文档.md` |
| 规格 / 交接 / 工作流 / 评审 | AI 派生 | `SPEC.md` / `HANDOFF.md` / `WORKFLOW.md` / `HARNESS_REVIEW.md` |

**优**:文件树视觉一秒分清"该不该亲审";AI 派生文档保持英文,hook/script 大部分不改;style-refs 已有先例。
**劣**:registry 的 `human_doc_patterns` 字段要双名兼容期(见 ADR-006);存量 13 个文档要 git mv。

## 选定

**C**。

理由:
- 视觉区分价值真实(用户已实测被英文命名混淆)
- 迁移成本可控(只动人类向 2 类,AI 派生 4 类不动)
- style-refs 已经先行,有可参照样本

## 后果

**优**:
- 文件树打开即知"这是要讨论的还是要查阅的"
- AI Step 4 收尾不会误改人类讨论文档
- 新任务从模板创建即用中文名,无需事后改

**劣**:
- 跨平台 git log 在某些 terminal(如老版 Windows cmd)中文显示乱码——但所有现代 IDE / Git Bash / VS Code 均正常
- registry / hook / 脚本要双名兼容期(由 ADR-006 兜底)

**风险**:
- 中文文件名在某些 CI / 容器镜像里 locale 缺失导致 path 解析失败 → 本任务用本地开发,不涉及 CI;若未来上 CI,设 `LANG=zh_CN.UTF-8`
- 跨任务统一性:所有任务都用 `需求分析.md` / `设计文档.md`,而非每个任务独立命名(对比 style-refs 的 `【需求分析】XX.md`)——任务名信息已在父目录,文件名不重复携带
