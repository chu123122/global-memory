### 1.3 信任边界(三层强度)

不是所有规则都能/应该靠 hook 强制阻断。架构必须明确**哪条规则用哪种强度执行**——这是 RULE_ENFORCEMENT_MATRIX 的核心字段。

| 强度 | 名称 | 谁执行 | 失败行为 | 适用 | 示例 |
|---|---|---|---|---|---|
| **S1** | 硬阻断 | hook (PreToolUse) | deny / ask | 危险/不可逆动作 | rm -rf / 改 CLAUDE.md / 改 implementation 阶段无 SPEC 任务的代码 |
| **S2** | 软校验 | 脚本 / CI | warning + 退出码 | 可绕过但应警告 | memory 超 50 / 文档漂移 / commit 无 SPEC 关联 |
| **S3** | 文档约定 | AI 自觉 + 同行 review | 仅记录,不阻断 | 风格/口吻/审美 | HUMAN_DOC_STYLE 风格、commit message 格式 |

**关键原则**:**S3 不能升 S1**——文档风格不靠 hook 卡(否则 AI 写每段文字都被打断);S1 不能降 S3——危险命令不靠 AI 自觉。每条规则 enforce 在哪一层是设计决策,记入 RULE_MATRIX。

### 1.4 横切设计原则(所有 Phase 必须遵守)

| # | 原则 | Why | 对应 ADR |
|---|---|---|---|
| 1 | **JSONL 而非 markdown** 作为机器可读载体 | 避免 memory 膨胀;机器可读;天然支持 append + 轮转 | ADR-001 |
| 2 | **registry 单一数据源** | 所有脚本/hook/skill 读 `~/.claude/~/.claude/projects/project_registry.json`,禁止 hardcode 路径/任务列表 | ADR-002 |
| 3 | **smoke_test_id 共享 schema** | RULE_MATRIX 与 smoke_test_hooks 通过这个字段对账;Phase 3 反向回填 | ADR-003 |
| 4 | **中文人类向 + 英文 AI 派生** | 文件树视觉一秒分清"要讨论的"和"自动生成的" | ADR-004 |
| 5 | **JSONL append-only,不就地改** | 历史不可篡改;面板用 last_offset 增量读;轮转走"按文件大小/行数"+"保留 N 份" | ADR-005 |
| 6 | **变更兼容期 + 拆 commit** | 任何 schema/约定变更都给迁移留缓冲(双名/双通道并行),不允许原子切换 | ADR-006 |
| 7 | **registry 字段 schema_version** | JSONL 与 registry 都标 schema_version,reader 按 version 兼容 | ADR-007 |

详细决策推理在 `decisions/ADR-NNN-*.md`。

| 观察对象 | 载体 | 写入者 | 消费者 | 实时性 |

### 1.7 架构治理规则(三条,等同于横切原则的元规则)

不仅设计要遵守原则,**架构本身的演化也要有规则**——否则架构会悄悄漂移成"做着做着就变样了"。

**规则 G1:架构允许演化,但要有触发条件**
- 允许改 §1.4 横切原则的情况:
  - 两个以上 Phase 出现同样的违反/绕过 → 反思原则,而非反复打补丁
  - Phase 实战暴露原则不可执行 → 走新 ADR 记录调整,旧 ADR 标 `Superseded by ADR-NNN`
- 不允许:**Phase 详细设计阶段悄悄改 §1**——必须显式提出"我要改 §1.4 第 N 条,新 ADR 见 XXX",用户审过才能改

**规则 G2:Phase 详细设计必须显式引用 §1 + ADR**
- 每个 Phase §N 的设计文档前几行强制写"引用区":
  ```
  本 Phase 落实 §1.4 横切原则:第 1/3/5 条
  本 Phase 消费/产出:§1.5 的 task_outcomes.jsonl(写入端)
  本 Phase 引用 ADR:ADR-001 / ADR-003 / ADR-005
  ```
- **没有引用区 = 在搞独立王国**,§1 会变成 decoration

**规则 G3:ADR 不可删,只可 supersede**
- 决策错了不改原 ADR,新写一个 ADR-NNN 标 `Supersedes ADR-XXX`,旧 ADR 顶部加 `**[已废弃]** 见 ADR-NNN`
- 这样 grep 历史能完整看到"为什么从 X 改到 Y",避免重复犯错

### 3.0 前置:`_lib.py` 工具新增(Phase 4-A 实现的真实依赖)

> **REVIEW-2026-04-24-1601 修订**:之前 §3.3/3.4/3.5 声称"复用已有的 `_atomic_append_jsonl` / `rotate_log` / `is_windows`"——**实测 `_lib.py` 里都不存在**(只有 `now_str / today_str / git_last_modified / extract_yaml_field / scan_topic_files / count_all_memory_files / write_log` 7 个函数)。同样 `portalocker` 也不在任何 requirements 里。Phase 4-A 必须**先把这 4 个工具加进 `_lib.py`**,再写 `outcome` 子命令。

**工具清单**(全部新建,无第三方依赖,纯 stdlib):

| 工具 | 签名 | 行数估算 | 平台分支 |
|---|---|---|---|
| `is_windows()` | `() -> bool` | ~3 行 | `platform.system() == 'Windows'` |
| `_file_lock(fp, exclusive=True)` | context manager | ~25 行 | Windows: `msvcrt.locking()`;POSIX: `fcntl.flock()`(都是 stdlib) |
| `_atomic_append_jsonl(path, record)` | `(Path, dict) -> None` | ~20 行 | 内部用 `_file_lock` + `open('a')` + `json.dumps + '\n'` |
| `rotate_log(path, max_size_bytes, max_lines, keep)` | `(Path, int, int, int) -> bool` | ~30 行 | 跨平台,纯 `os.rename`;按 size 或 lines 任一超限触发 |

**为什么不引入 `portalocker`**:
- 增加第三方依赖,部署时多一道 pip install,且 portalocker 本身就是封装 stdlib 的 fcntl/msvcrt
- 我们的写入频率是"任务完成时一次"(日均 1-2 次),并发风险极低,stdlib 完全够
- 如果未来证实 stdlib 锁有 corner case,再走 ADR-008 升级到 portalocker

**测试**(新建 `harness/tests/test_lib.py`):
- `test_is_windows_returns_bool` — 类型校验
- `test_atomic_append_single_writer` — 单进程 100 次 append,验证行数 = 100 且每行合法 JSON
- `test_atomic_append_concurrent` — `multiprocessing.Pool(5)` 各 append 20 行,验证总行数 = 100 且无错乱
- `test_rotate_by_size` — 写入超过 max_size_bytes,验证 .1 文件出现且原文件清空
- `test_rotate_by_lines` — 同上但按行数
- `test_rotate_keep_n` — 写满 N+1 次,验证最旧的被丢弃

**Phase 4-A.0 vs Phase 4-A.1 不另起命名**——这些工具是 Phase 4-A 实现的**第 1 步**,不算独立 Phase;但执行顺序上必须先于 §3.3 的 `outcome` 子命令实现。

### 3.2 Schema v1(7 字段最小集)

```json
{
  "schema_version": 1,
  "ts": "2026-04-24T17:30:12Z",

  "phase": "0",
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schema_version` | int | ✅ | 当前 1;未来 reader 按 version 兼容 |
| `ts` | ISO 8601 string | ✅ | UTC 时间戳,reader 跨时区一致 |
| `task` | string | ✅ | 任务名,与 `project_registry.json` 的 `active_tasks` 项对齐 |
| `phase` | string | 可选 | Phase 标识(如 `"0"` / `"1-A"` / `"4-A"`);单 Phase 任务可省。**reader 缺值处理**(REVIEW 修订):缺失 → 视为 `"main"`(全任务级别记录);Phase 4-B reader 按此约定聚合 |
| `outcome` | enum | ✅ | `completed` / `partial` / `abandoned` / `blocked` |
| `metrics` | object | ✅ | 5 个核心指标(见下) |
| `lesson` | string | 可选 | 一句话教训;空值表示无显著教训 |

**metrics 子字段定义**:

| 子字段 | 含义 | 来源 | 缺值默认 |
|---|---|---|---|
| `rework_count` | 本任务期间被推翻重做的次数(用户说"撤销 / 重做 / 不对") | 人工估算或从 git revert 数 | 0 |
| `tool_calls` | 工具调用总次数 | 从 `tool_audit.jsonl` 按 task window 聚合(本期手填,Phase 4-B 自动) | 0 |
| `doc_gate_blocks` | doc_gate 拦截次数 | 同上,从 audit 聚合 | 0 |
| `memory_writes` | global-memory 文件被改的次数 | 从 git log 聚合 | 0 |
| `duration_min` | 任务从开始到完成的钟表时间(分钟) | 人工估算 | null |

**字段克制**:本期不加 `failure_reason_classification` / `task_type` / `tags`——避免 schema 早期反复改;后续若发现统计需求再走 ADR + bump schema_version。

### 3.4 轮转策略(落实 ADR-005)

`panel_api.py outcome` 在每次 append 前检查目标文件:
- 文件大小 ≥ 5 MB 或行数 ≥ 10000 → 滚动:`task_outcomes.jsonl.2` 删除 → `.1 → .2` → `.0 → .1` → 新空文件
- 保留最近 3 份(`.0` / `.1` / `.2`)

**实现**:调用 §3.0 新增的 `rotate_log(path, max_size_bytes=5*1024*1024, max_lines=10000, keep=3)`。

**实战阈值反思**(REVIEW 修订):账本日均 1-2 条,5 MB / 10000 行实际意味着**几年才轮转一次**——本期轮转代码近乎死代码,只有 4A-V4 mock 测试触发。考虑把 `rotate_log` 的实际调用从 `outcome` 子命令里**摘掉**,只留 `_lib.py` 工具实现 + 单测;真正的轮转判定推到 Phase 4-B reader 启动时做(reader 反正要扫文件,顺手判轮转更自然)。这一改动作为 §3.4 的 trade-off 选项,留待 Phase 4-A 实现时和用户对齐(默认按"内置轮转,实战死代码"实现,因为 ADR-005 已定型)。

### 3.5 并发与原子性(落实 ADR-005 风险)

调用 §3.0 新增的 `_file_lock(fp, exclusive=True)` context manager,内部按 `is_windows()` 分流:

| 平台 | 锁实现 | 模块 | 备注 |
|---|---|---|---|
| Windows | `msvcrt.locking(fp.fileno(), msvcrt.LK_LOCK, n_bytes)` | `msvcrt`(stdlib) | LK_LOCK 阻塞获取;LK_UNLCK 释放 |
| POSIX(Linux/macOS) | `fcntl.flock(fp.fileno(), fcntl.LOCK_EX)` | `fcntl`(stdlib) | LOCK_EX 排他锁;close 时自动释放 |

**REVIEW 修订**:之前说"写一个 50 行的 fcntl-fallback"是错的——`fcntl` 是 POSIX-only 模块,在 Windows 上 `import fcntl` 直接抛 `ModuleNotFoundError`,不能作 Windows 兜底。**正确做法是按平台分支选 `msvcrt` 或 `fcntl`,二者都是 stdlib,不引入第三方依赖**。

**为什么不依赖 `open('a')` 在 POSIX 的"<PIPE_BUF 单行 append 原子"特性**:
- 跨平台代码不应假设 POSIX 语义(Windows 没有 PIPE_BUF 概念)
- 显式锁让代码意图清晰,不依赖隐式语义
- 性能开销可忽略(锁的获取释放 < 1ms,而账本写入是低频)

### 3.7 Phase 4-A 与 Phase 0 的执行序冲突说明

按重排,Phase 0 在执行序 1,Phase 4-A 在执行序 2。但 Phase 4-A 的 4A-V5(**自身写第一条**)需要 Phase 0 完成。怎么办?

**处理**:Phase 4-A 设计 + 实现可以与 Phase 0 并行(代码不冲突);但 4A-V5 必须等 Phase 0 完成后才能跑。流程:

```
Phase 0 实现 ─→ Phase 0 commit 1/2/3 完成 ─→ Phase 0 写第一条 outcome (4A-V5)
                                                ↑
Phase 4-A 实现 ──────────────────────────────────┘
```

实际执行时,可能的简化路径:
- 先做 Phase 0 commit 1(脚本支持中文名)
- 立刻做 Phase 4-A 实现(此时 Phase 0 commit 1 已就绪,registry 改完不影响 Phase 4-A)
- Phase 4-A commit
- 回到 Phase 0 commit 2(批量 mv)
- Phase 0 commit 3(清理 fallback)
- Phase 0 完成 → 跑 4A-V5 写第一条 outcome

### 3.8 风险与缓解

| 风险 | 现方案的代价 | 缓解 |
|---|---|---|
| schema v1 字段不够,后期反复改 | 历史数据无法直接重读 | schema_version 字段兜底,reader 按 version 兼容;ADR-007 形式化此规则 |
| AI 忘了在 Step 4 收尾时写 outcome | 该次任务没样本,数据丢失 | `/work` SKILL.md Step 4 强制提示;Phase 4-B 加"上次写入时间 > 1 天"的状态告警 |
| 用户手动估算 metrics 不准 | 度量噪音 | Phase 4-B 实现自动聚合(从 audit jsonl 反推);本期手填可接受 |
| Windows 锁失败导致行错乱 | 极少数情况下数据损坏 | §3.0 `_file_lock` 用 stdlib `msvcrt.locking()` (Windows) / `fcntl.flock()` (POSIX) 双路径;4A-V3 单测覆盖并发场景 |
| §3.0 stdlib 锁在某些 Windows 边缘场景失效(网络挂载、WSL 跨边界) | 罕见 corner case 漏锁 | 当前账本写入是单机 + 本地路径,不触及网络挂载;若未来发生再走 ADR-008 升级到 portalocker |
