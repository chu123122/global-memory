# global-memory 体系审计报告

> 审查时间：2026-04-28-1128
> 审查人：design-reviewer (opus, read-only)
> 审查目标：D:/global-memory 整体体系
> 证据基础：仓库实际状态 + 用户两轮访谈答案

---

## 1. 一句话判断

**「复杂的个人知识管理系统 + 尚未闭环的 AI 工作流实验」（偏向后者）**。

理由：基础设施（hooks / maintain.py / 控制面板 / CHANGELOG / ADR）远超普通个人项目，已经具备「会搭」的能力；但用户答案里的三个核心信号同时出现——
- 「记忆没参与思考决策」(Q12 / Q21)
- 「learning 基本没用过」「目前只是未来规划」(Q9 / Q43)
- 「daemon 失败 / S3 违反我都不知道」「上周五才启动这个规划」(Q35 / Q34 / Q40)

——意味着这套体系**当前以 harness 自身建设为主要产物**，主业（心动实习开发）和原本要服务的"学习"两条主线都没被它实际加速。`harness-governance-v1` 自己就是过去一周的最大用户。这不是 harness engineering 的失败，但确实还没闭环。

不能叫"有效的个人 AI harness"——因为用户自己讲不出 5 分钟救时间例子，也讲不出失败案例(Q9 / Q10)，属于价值不可证。

不能纯叫"个人知识管理"——因为它已经有 hooks / 信任边界 / smoke test / outcome ledger 这些 KMS 不会有的东西，KMS 不会写 `RULE_ENFORCEMENT_MATRIX.md`。

## 2. 当前核心优势（5 条，每条带证据）

1. **维护工具栈成熟、入口收敛干净**。`maintain.py` 用一个 CLI 统一了 doctor/fix/sync/daemon/log/report，文档（MAINTENANCE.md）写得极清晰，每个子命令是否改文件、是否 commit/push 都有边界表（MAINTENANCE.md L91-101）。这层比绝大多数个人脚本目录强。
2. **规则到执行的显式映射存在**。`RULE_ENFORCEMENT_MATRIX.md` 14 行覆盖 8 hooks + 6 hard rules，强度 S1/S2/S3 + enforcer + failure_behavior + smoke_test_id 的 schema 设计是 harness engineering 教科书级的产物，多数个人项目根本不会做这一步。
3. **AI 写盘有 hard guardrails**。`PreToolUse Write|Edit` 链路上挂了 `memory_file_protector`（改 CLAUDE.md/agents 弹确认）+ `doc_gate`（按 task Status 阶段检查必填文档）+ `diff_backup`（白名单内 Edit 前自动备份），这是真正避免 AI 误改全局规则的关键防线。`STATUS_SNAPSHOT.md` 显示 memory_file_protector / doc_gate / dangerous_command_blocker 都有最近触发记录（2026-04-24）。
4. **CHANGELOG 是真在用的审计日志**。最近 50 行不是机械填模板，而是带根因/验证/残余风险的人话记录（如 2026-04-28 11:22 diff_show 修复条目结构完整）。这条机制目前是体系里复用率最高的产物。
5. **/work 文档防线 + 中文 / 英文双轨命名（ADR-004）已经落地**。三层防线（check_doc_status → doc_gate hook → check_doc_sync）+ 中文人类向 / 英文 AI 派生的命名约定，是用户自己反复迭代后留下的最有用的工程化结论之一，且用户在 Q33 明确说"主要看后续新加的中文人类文档"——这是少数被实际使用的产物。

## 3. 当前核心问题（5 条，每条带风险）

1. **整套体系的 ROI 不可证**。用户 Q9/Q10 都说"没太多直观感觉"——既说不出救时间例子，也说不出拖慢例子。当一个人花上百小时建的系统讲不出任何具体收益时，要么是收益太小，要么是没有度量手段，两者都是危险信号。`task_outcomes.jsonl`（Phase 4-A）正是为解决这个问题加的，但 Q44 用户说「好像偶尔会用？」——度量机制本身没被用起来。
2. **「三层记忆」概念在用户脑子里和文档里完全对不上**。README 写的是"记忆层 / 工作流层 / Harness 层"（结构层），用户 Q19 答的是"短期 / 长期记忆"（时间层）。这是**命名漂移 + 模型不共识**双失效，意味着用户其实没有在用这个抽象做日常决策——这条详见 §4。
3. **knowledge/ 极可能是只写不读的归档区**。8 个 `knowledge_*.md` 文件 7 个 `access_count: 0`，只有 `knowledge_system_design.md` 是 2，且 30 篇 `docs/*.md` 加在一起 643KB。用户 Q47 自己说"不确定 knowledge 是否被复用"。CLAUDE.md 里写"C++ 多线程/面试/UE 底层相关正式任务前先读对应 knowledge/"，但没有任何机制验证 AI 真的读了——`access_count` 字段本身没有自动更新逻辑。这是典型的"理论上重要，实际上死代码"。
4. **daemon + 自动同步是无监管的高副作用机制**。`maintain.py` L573 在 `pull --rebase` 失败时返回 `synced=False, summary="pull --rebase failed; aborting push"`——但这条失败信息只写到 sync log，**没有任何 surface 把它推到用户面前**。用户 Q36 答"不知道怎么处理"。最坏情况：远端冲突日积月累，本地 ahead 越拉越多，某次手动 push 时被迫强解；或反向，daemon 在不该 push 的时候 push 了被污染的 checkpoint。`STATUS_SNAPSHOT.md` 自己显示 28 个 dirty 项 + post_task_hook "no log yet"，说明同步链路本身就有"看起来在跑实际不知道"的问题。
5. **harness 自身建设挤占主业**。Q8 列的高频 work 任务全是"自我迭代 / 个人博客优化 / 插件重构"，**没有一条是心动实习的多线程资源加载插件**——而那是 CLAUDE.md 第 9 行明确写的"第一个入职任务"。`projects/` 目录下 active 任务有 8 个（STATUS_SNAPSHOT），其中 `harness-governance-v1` / `control-panel-v1` / `control-panel-v2-pyside` / `diff-workflow-redesign` 4 个都是 harness 自身。手段在挤占目的。

## 4. 三层记忆审查

### (a) 命名漂移本身就是问题

- README L9-15 的"三层"是**结构性分层**：记忆层（存什么）/ 工作流层（怎么做）/ Harness 层（怎么落地脚本）。
- 用户 Q19 给的是 **时间性分层**：短期 / 长期。两者完全不是同一个轴。
- Q20 用户进一步说"感觉意义不大，记忆也没参与思考决策"——**当用户连自己系统的核心抽象都说不准、还说意义不大时，这个抽象已经死了**。要么文档错（应该改 README 不再叫"三层"），要么用户错（应该重新培训自己），不能两边都漂着。

### (b) 按 README 实际三层逐层评

| 层 | 用途清晰度 | 更新机制 | 检索有效性 | 污染风险 | 是否值得保留 |
|---|---|---|---|---|---|
| **记忆层** (`MEMORY.md` + feedback/knowledge/fixes/decisions/interview) | 中。MEMORY.md 80 文件上限、AUTO-INDEX 自动生成的设计是清楚的，但用户 Q23 说"MEMORY.md 职责不确定，没太管" | 强。`sync_index.py` + `update_stats.py` + CHANGELOG 强约束 | **弱**。8/8 knowledge 文件 access_count 几乎全是 0；feedback/ 11 个文件全部 2026-04 创建，最近高频更新但用户 Q33 自己说"基本不看"AI 派生文档 | **中-高**。MEMORY.md 已 60/80，AUTO-INDEX 区段每次都被全量 rerender 进 prompt，正在膨胀 | **保留但收缩**。这层不能删，但要明确收缩 |
| **工作流层** (`agents/` + `skills/` + `templates/`) | 高。/work 入口 + Status 阶段感知是少数闭环成功的设计 | 中。skills 改一次要同步 verify_prompt_system + bootstrap，但用户 Q40 答"S3 违反我发现不了"说明 skill 行为漂移没监管 | **不均匀**。`/work` 真用，`/learn` 是上周才补的（CHANGELOG 2026-04-28）且用户 Q43 说"未来规划"，`/check`（你正在跑的）真用 | 低。skill 数量可控（11 个），junction 部署清晰 | **保留，是体系最值钱的层** |
| **Harness 层** (`bootstrap.py` + `check_health.py` + `harness/`) | 高。MAINTENANCE.md 把每个脚本的边界、命令、退出码都写清楚了 | 中。`harness/` 73 个 .py，自身已经达到一个小项目规模；test 覆盖只有 6 个 test 文件 | 中。maintain.py 是真入口，但 daemon 失败用户感知不到（§3.4） | **高**。脚本数量正在膨胀，`control_panel.py` + `control_panel_pyside/` 两套 GUI 同时存在（v1 tk + v2 pyside），就是上周漂移出来的 | **保留但必须 GC**。砍 v1，砍冷脚本 |

### (c) 整改建议

1. **重命名"三层"** → 改叫 **"持久化 / 工作流 / 运行时"**（Persistence / Workflow / Runtime）。"记忆层"这个词在 LLM 语境里太容易和 short-term/long-term context 混淆，正是用户 Q19 翻车的根因。改名后 README L9-15 表格同步重写。
2. **不删任何一层，但按层加一句"何时应该读"**。例如：持久化层只在「正式任务启动协议 / 用户说"记得我之前讨论过" / `/work continue`」三种触发下才读；其余场景不允许 AI 主动读 MEMORY.md。这能立刻把"AI 读了什么不确定"（Q26）的问题压住。
3. **拆而不并**：MEMORY.md 当前同时承担「索引 + 活跃项目交接 + 系统规则索引 + 项目索引 + 复盘索引 + AUTO-INDEX 表 + 统计」7 件事，违反单一职责。建议拆出 `ACTIVE_PROJECTS.md`（前 30 行）+ `MEMORY_INDEX.md`（AUTO-INDEX 区），MEMORY.md 只留入口跳转。这能让"启动协议必读 MEMORY.md"实际只读 30 行，不再每次塞 250 行进 prompt。
4. **删一层的候选**：knowledge/docs/ 30 篇深度文档（643KB）。用 access_count=0 + 用户"不确定是否复用"的双重证据，建议**整体迁移到 archives/cold-knowledge/**，从 MEMORY.md 索引摘除，只在 `/learn` 显式触发某话题时按需 Glob。这一动作能给 AI 的 context 上限省出可观空间。

## 6. 最危险的 3 个失效模式

### M1：daemon 静默同步坏数据
- **触发条件**：`auto_sync_daemon.py` 在用户离开电脑时 idle 5 分钟 → 触发 `maintain.py sync --source daemon` → `pull --rebase` 因远端有冲突 / 多设备并发 push 而失败 → 脚本正确 abort，但只写 sync log
- **后果**：本地 ahead 持续累积；下一次用户手动 push 时被迫处理几天的冲突；最坏情况是用户在另一台设备 push 了关键 ADR 更新，本地 daemon 一直 abort 但没人看，导致两边永远不同步
- **早期信号**：`STATUS_SNAPSHOT.md` 显示 `behind > 0` 持续不归零 / `auto_sync.log` 末尾连续 N 条 `pull --rebase failed`
- **预防方式**：daemon 失败时强制写一条 `panel_api.py notify --level warning`，让控制面板「事件」页弹红字。**rebase 连续失败 3 次自动停止 daemon 并发系统通知**

### M2：MEMORY.md 过载 → AI 选择性失明
- **触发条件**：`MEMORY.md` 当前 60/80（README L83），AUTO-INDEX 区每加一个文件就多一行，启动协议要求 AI 必读 → AI 把 ~250 行索引塞进 context → 用户问具体问题时 AI 因 context 压力跳过对应文件实际内容
- **后果**：用户感知是"AI 这次怎么没记得我上次说的 X"，但根因是 AI 看见了索引项却没读详情，且用户 Q26 答"AI 读了什么不确定"——意味着这个失效正在发生且无法定位
- **早期信号**：用户开始抱怨 AI"忘了"上下文 / AI 在 /work 启动时频繁问"上次做到哪了"
- **预防方式**：①拆 MEMORY.md（见 §4(c).3）②AUTO-INDEX 加 `last_accessed` 字段，30 天未读自动迁 archives ③在 stop-hook 里把"AI 本轮实际 Read 了哪些 memory 文件"日志化，用户能事后核对

### M3：harness 自身建设永久挤占主业
- **触发条件**：`/work` 流程对所有任务一视同仁 → 用户每次想推进心动实习多线程插件时，看到"还能再优化下控制面板"的诱惑就转去做了
- **后果**：入职第一个任务（多线程资源加载插件）持续 0 进度；与此同时 harness 仓库继续膨胀（已 73 个 .py + 11 个 skill + 6 个 agent + 8 个 active task）；2026-07 入职时拿不出主业产出
- **早期信号**：active_tasks 列表里 harness 类任务占比 ≥ 50%（**当前 4/8 = 50%，已经触发**）/ CHANGELOG 最近 20 条全是 harness 改动（**当前 50 行确实如此**）
- **预防方式**：① `project_registry.json` 加 `category: business / harness / personal` 字段；② `/work` 启动时如果 active business 任务进度 < 上周 → 警告"过去 7 天主业 0 进度，是否继续 harness 任务？"；③ 给自己定**硬规则：active harness 任务 ≤ 1**（当前 4，超 4 倍）

## 7. 被高估的部分

1. **「三层记忆」抽象**——见 §4。用户自己讲不出，文档自己漂移，留着只会持续误导。
2. **S1/S2/S3 信任边界分级**——schema 设计漂亮，但 S3 (RULE-010 ~ 014) 全部 enforcer = AI/human + smoke_test_id = manual。Q40 用户答"我发现不了 S3 违反"。一个**用户既不感知违反、也无机制审计**的分级，等于不存在。S2 (RULE-009) 也只有 1 条。**真正生效的只有 S1**——那为什么不直接叫"hard rule / soft rule"两级，砍掉 S3 这个"自我安慰层"？
3. **knowledge/docs/ 30 篇深度文档（643KB）**——见 §3.3。access_count 全 0，用户 Q47 自承认"不确定复用"。这是过去几个月堆积的"看起来很 senior"但没人读的产物。建议整体冷藏。
4. **daemon 自动同步**——Q35 用户答"上周五才启动这个规划，没安全感也没风险感"。一个新机制 + 没有失败回归测试 + 失败用户无感（M1）= 净负价值。手动 `maintain.py sync --source manual` 已经够用，daemon 在用户能 hold 住前应该停掉。
5. **harness-governance-v1 元工程本身**——8 个 ADR + Phase 0~5 + smoke_test 框架，对一个个人 harness 来说已经过度工程化。它解决的"看不见 hook 是否真触发"问题确实存在，但**先让用户能用起来 task_outcomes.jsonl 一周再说**——目前 outcome ledger 写入端实现了、reader 实现了、面板入口加了，用户答"偶尔会用"（Q44）。这个项目消耗了过去一周大部分注意力（CHANGELOG 印证），但用户答"3 层记忆没体现出"——投入产出严重失衡。

## 8. 被低估的部分

1. **中文人类向文档（ADR-004 + style-refs/）**——用户 Q33 直接说"主要看后续新加的中文人类文档，其他基本不看"。这一条决策可能是过去一个月最值钱的产物，因为它是**唯一被用户 self-reported 真实使用**的产物。但目前在 ADR-004 里平等地和"JSONL append-only rotation"放在一起，没被识别为**最高 ROI 决策**。
2. **`/work` skill 入口**——用户 Q33 答"文档有用"。和 ADR-004 一起，这是体系真正在用的两块。但 `/work` 当前文档里 Step 0/1/2/2.5 加起来已经 80 行，`work_context_pack.py` + `check_doc_status.py` + `check_doc_sync.py` 三个脚本，复杂度还在涨。**简化它而不是继续加，会比再写一个新 skill 更值**。
3. **CHANGELOG.md 的强约束 + 真实人话条目**——50 行最近条目质量极高（根因 / 验证 / 残余风险都齐），相比之下 `STATUS_SNAPSHOT.md` 是机器生成的死表。CHANGELOG 才是这套系统**真正的运行时事实来源**。建议每周从 CHANGELOG 自动生成一份"本周做了什么"摘要喂给下一周对话。
4. **retrospectives/**——只有 1 个文件（retro_2026-04-14_blog-music-player.md，Q47 验证为真）。这是被严重低估的实践——5 行复盘比 5 个 Phase 的 ADR 价值高，因为它强制回答"实际做完后跟设计差多少"。建议**每周固定写 1 篇 retro，目标比 ADR 高 3 倍**。
5. **HUMAN_DOC_STYLE.md + style-refs/ 的强制 Read**——work skill Step 1.3 强制要求写人类文档前 Read 风格参考。这是**唯一一条 S3 实际生效的规则**（因为脚本 + AI 都 enforce），证明 S3 配合 skill workflow 是可以做出真效果的，但目前只用在写文档这一个场景。

## 9. 优先级最高的 5 个改进（按 ROI 排序）

| # | 动作 | 预期收益 | 执行成本 | 风险 |
