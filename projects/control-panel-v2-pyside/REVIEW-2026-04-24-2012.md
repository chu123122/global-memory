## 2. 技术风险 — 🟡

**发现**：

1. **`summarize_outcomes` / `summarize_recent_events` 接口契约缺失（preflight 已检出 placeholder）**（设计 §2 第 50-60 行，确认）
   - 经 `Grep` 实证：`~/.claude/global-memory\harness\control_panel_model.py` 中**完全不存在**这两个函数（仅有 `summarize_status / doctor / sync_preview / log / event` 5 个）。
   - 设计 §2 第 60 行"若 4-B 长期未就绪，账本页退化为 placeholder"是正确的降级路径，**但 SPEC §7 进度记录写"5 个 summarize_* 接入完成（model 层零改动）"** 与设计 §2 的"待 Phase 4-B 提供"自相矛盾——实际接入的是 status/doctor/sync_preview/log/event 这 5 个**已存在的**，而非 outcomes/recent_events。SPEC §7 的"5 个"是对 §3"5 个 summarize_* 接入"的复述，但读者会误以为包含 outcomes。
   - 实证：`conclusion_panel.py` 仅含一处文档串 `summarize_*('decision')`，并未实际 import outcomes/recent_events；`main_window.py` 也无 outcomes 引用。即"账本页 placeholder"路径**已隐式生效**，但无任何代码或注释明确标记"等待 4-B"，实机用户面对空白会无从判断是 bug 还是 placeholder。
   - 风险：harness-governance-v1 Phase 4-B 推出后，schema 若与 v2 的隐式假设不符，需要重做渲染层；目前没有任何 contract test / mock 数据来锁定预期。

2. **JSONL 半行容错与 `consumed_bytes` 推进口径不一致风险**（设计 §3.2 vs polling.py:84）
   - 设计 §3.2 伪代码用 `consumed += len(line.encode("utf-8")) + 1` 推进 offset；实际实现 `polling.py` 也按此口径。
   - 隐含约束：`f.read()` 在文本模式下返回 `str`，`f.tell()` 与字符数不直接对应；当文件含 CRLF（Windows 默认）+ utf-8 多字节字符时，`len(line.encode("utf-8")) + 1`（+1 假设 LF 单字节）在 CRLF 行尾会少算 1 字节，**累计若干行后 last_offset 会落后于真实文件位置**，可能造成"重读已处理行"——对幂等渲染影响有限，但事件页可能出现重复条目。
   - 设计文档未对"文件以 CRLF 写入还是 LF 写入"做硬约束；panel_api.py 在 Windows 上默认会把 `\n` 翻成 `\r\n`（除非显式 `newline=""`）。建议文档加一条强约束。

3. **git status 走 QThread 但未声明并发上界**（设计 §3.1 git 通道）
   - 10s 周期 + Windows cold cache 800ms，绝大多数情况安全；但若用户切到守护页（假设触发 git status）+ 主动刷新 + 后台轮询同时发起，可能并发多个 subprocess。
   - 设计未规定"同一时刻最多 1 个 git 子进程在跑"。建议加 `_busy` 标志或 QThreadPool maxThreadCount=1。

4. **PyInstaller `--onefile` 启动 3-5s + Win Defender 首次扫描**（设计 §8.2）
   - 估计合理，但未提"用户首次双击 .exe 时的 SmartScreen 警告处理（个人未签名）"。Win10/11 默认会蓝屏 SmartScreen 拦截未知发布者 .exe，"手动放行"对非技术用户友好度低；用户已明示自用，OK，但建议在 SPEC §3 V1 验收旁加"首次启动需在 SmartScreen 选'仍要运行'"。

5. **HANDOFF §7 已声明 `qdarktheme` 包名换成 `pyqtdarktheme-fork`，但 SPEC §6/§8 `requirements.txt` 仍写 PyQtDarkTheme**
   - 实际 requirements.txt 应写 `pyqtdarktheme-fork>=2.3`，HANDOFF 已澄清"设计文档不回改"，但 SPEC 也需对齐。否则按 SPEC 拉的依赖跑不起来。

**建议**：
- **R2.1**：设计 §2 / SPEC §6 把"待 4-B"接口名加上 ⚠️ 标记并指向"placeholder 行为"；conclusion_panel.py 增加显式占位 widget（"等待 harness-governance-v1 Phase 4-B reader"），不要让用户面对空白白板。同时建一份 `samples/outcome_v0.jsonl` 锁住目前预期 schema，4-B 落地时做契约校验。
- **R2.2**：polling.py 改用二进制模式 `open(path, "rb")` + `decode("utf-8")` 后再 split，offset 用 `f.tell()` 直接拿；或在文档/代码里明确"panel_api 必须以 LF（newline=''）写入"。当前 5/5 单元测试是否覆盖了 CRLF 文件？建议加一个 CRLF fixture 用例。
- **R2.3**：cli_invoke.run_async + git 通道加并发上界（QThreadPool.setMaxThreadCount(1) 或 _running 标志位）。
- **R2.4**：SPEC §6 `requirements.txt` 行改写 `pyqtdarktheme-fork>=2.3`，与 HANDOFF §7 对齐。
