## 二、预测回滚完整架构（对标你的实现）

### 2.1 核心流程

```
客户端每帧：
  1. 收集本地输入
  2. 预测对手输入（默认=上一帧）
  3. 用预测输入执行一帧模拟
  4. 保存状态快照
  5. 发送本地输入到服务端

收到服务端确认输入：
  6. 比对预测输入 vs 实际输入
  7. 一致 → 继续（无开销）
  8. 不一致 → 回滚到最后确认帧 → 用正确输入重新模拟 → 追帧到当前帧
```

### 2.2 你的实现 vs GGPO vs 行业实践

| 模块 | 你的实现 | GGPO | 行业最佳实践 |
|------|---------|------|-------------|
| **快照** | 环形缓冲区 64 帧 | 内部状态保存 | ✅ 环形缓冲区是标准做法 |
| **回滚深度** | 最大 15 帧 | 无硬限制 | 通常 7-15 帧，守望先锋用 7 |
| **预测策略** | 复制上一帧输入 | 复制上一帧输入 | ✅ 标准做法 |
| **回滚后平滑** | 渲染插值 LERP | 不做（格斗不需要） | ✅ 非格斗游戏需要 |
| **哈希校验** | 每帧计算 | 每帧计算 | ✅ 确定性验证 |
| **Input Delay** | 5 帧固定 | 可配置 | ⚠️ 应动态调整（见下文） |

### 2.3 你缺少的：动态 Input Delay / 预测 Buffer

**守望先锋 GDC 分享的核心优化**：

```
网络好时（RTT低）：
  → 减少预测帧数 → 回滚概率低 → 体验好
  
网络差时（RTT高）：
  → 增加预测帧数 → 保证流畅但回滚可能更深

动态调整：
  Input Delay = ceil(RTT / (2 * frameTime)) + 1
  例如 RTT=100ms, 帧时间=33ms → delay = ceil(50/33)+1 = 3 帧
```

**面试话术**：
> "我的实现用了固定 5 帧 Input Delay，这是权衡简单性和响应性的结果。更优的做法是根据 RTT 动态调整——网络好时减少 delay 提高响应性，网络差时增加 delay 减少回滚次数。守望先锋的做法是 delay = ceil(RTT/2/frameTime) + 1。"

## 三、RUDP 实现对比

### 3.1 你的 RUDP vs UE 的 RUDP vs KCP

| 特性 | 你的实现 | UE RUDP | KCP | GGPO |
|------|---------|---------|-----|------|
| **序列号** | 16 位 | 14 位（回绕） | 32 位 | 自定义 |
| **ACK 机制** | ACK bitfield | ACK + History(256位) | ACK + UNA + SN | InputAck |
| **重传** | 超时重传（指数退避） | **Nak 驱动重传**（无 RTO） | 快速重传 + RTO | 定时重传(200ms) |
| **保序** | 接收去重 | 两层保序（Packet+Channel） | 自动保序 | 应用层保序 |
| **拥塞控制** | 无 | QueuedBits 饱和检测 | 无（设计意图） | 无 |
| **RTT 测量** | EWMA 平滑 | 延时 ACK 隐含 | EWMA + 抖动 | QualityReport |
| **连接管理** | 无 | 完整状态机 | 无 | SyncRequest 握手 |

### 3.2 UE RUDP 的独特设计（面试重点）

**1. 两层保序**
```
Connection 层：PacketOrderCache（环形缓冲区，默认3个）
  → 处理 Packet 级别的乱序
  
Channel 层：InRec 链表队列（上限256个）
  → 处理 Bunch 级别的乱序
```

**2. Nak 驱动重传（无 RTO）**
UE 的 RUDP 没有超时重传！全靠 Nak（否定确认）：
- History 256 位 → 每个 Packet 都有明确的 Ack/Nak 反馈
- Nak → 立即重传对应 Bunch
- 好处：不浪费时间等超时，响应更快

**3. 混合 ACK 策略**
- 主要：随回包捎带 AckSeq（低开销）
- 托底：tick 驱动的延时 ACK（防止没有回包时 ACK 延迟）

**面试话术**：
> "UE 的 RUDP 有个独特设计——它没有 RTO 超时重传。因为它用 256 位的 History 位数组追踪每个包的 Ack/Nak 状态，每个包都有明确反馈，所以直接用 Nak 驱动重传，比等超时更快。我的 RUDP 用了超时重传作为兜底，这是更保守但更简单的做法。"

### 3.3 KCP vs ENet vs 你的 RUDP

| | KCP | ENet | 你的 RUDP |
|---|---|---|---|
| 语言 | C | C | C# + C++ 对称 |
| 核心优势 | ARQ + 快速重传 | 可靠/不可靠信道并存 | 极简（12 字节 header） |
| 延迟 | TCP 的 30-40% | TCP 的 50-60% | 取决于重传策略 |
| 适用 | MOBA/棋牌 | FPS/MMO | 帧同步（你的场景） |
| 拥塞控制 | **故意不做** | 有 | 无 |

**KCP 不做拥塞控制的原因**：
> 游戏场景带宽很小（几十 KB/s），不需要拥塞控制。TCP 的拥塞控制（慢启动、拥塞避免）是为大流量设计的，反而增加了延迟。

## 四、确定性保证（帧同步的生命线）

### 必须保证的确定性因素

| 因素 | 问题 | 解决方案 |
|------|------|---------|
| **浮点数** | 不同 CPU 结果可能不同 | 定点数 or 严格 IEEE754 模式 |
| **随机数** | 不同客户端种子不同 | 服务端下发 master seed |
| **执行顺序** | 遍历 Dictionary 顺序不确定 | 用有序容器或 sort by ID |
| **物理碰撞顺序** | 碰撞对的处理顺序影响结果 | 按 EntityId 排序 |
| **Timer** | 基于真实时间的 Timer 不确定 | 全部改为基于帧步进 |

### 你的项目中的确定性措施

| 你做了 | 你没做 |
|--------|--------|
| ✅ EntityId 排序碰撞 | ❌ 定点数（用的 float） |
| ✅ 纯函数 SimulateFrame | ❌ 随机数种子同步 |
| ✅ 哈希校验 | ❌ 浮点一致性保证 |

**面试话术**：
> "浮点确定性是帧同步最大的挑战。我的项目目前用 float 加哈希校验——如果两端哈希不一致说明浮点分歧了。生产级方案会用定点数（Q16.16），但开发阶段用 float+hash 可以更快验证其他模块的正确性。"

## 五、断线重连

### 方案对比

| 方案 | 原理 | 延迟 | 带宽 |
|------|------|------|------|
| **全量快照** | 服务端发送完整世界状态 | 低 | 高（一次性） |
| **追帧** | 从 frame 0 开始快速重放所有输入 | 高（10 分钟游戏 = 18000 帧） | 中 |
| **增量快照+追帧** | 从最近检查点开始追帧 | 中 | 中 |

你的 ConnectionManager 用的是**全量快照方案**——最简单也最可靠。

## 六、GGPO 的关键设计

### 帧优势（Frame Advantage）

```
local_frame_advantage = remote_frame - local_frame
```

- 正值 → 本地落后，需要加速
- 负值 → 本地超前，需要减速
- GGPO 通过 QualityReport 交换帧进度，动态调整模拟速度

### 输入压缩（增量编码）

```
1. 比较当前输入和上次确认输入
2. 用 bitvector 标记变化的按钮
3. 用 nibble（4bit）编码变化位置
```

典型格斗游戏：每帧输入约 2-4 字节 → 压缩后约 1-2 字节

### 旁观者支持

旁观者用相同协议连接，但只接收不发送输入。确认帧被广播给所有旁观者。

## 七、面试高频题

### Q: 帧同步和状态同步的区别？
> "帧同步只同步输入，客户端各自模拟，要求确定性；状态同步同步状态结果，不要求确定性但带宽高。帧同步适合 RTS/格斗（实体多），状态同步适合 FPS/MMO。我选帧同步是因为项目需要确定性回放和低带宽。"

### Q: 预测回滚是怎么工作的？
> "客户端先用预测输入（复制上一帧）执行一帧并保存快照。收到服务端确认后，如果预测正确就继续；不正确就回滚到最后确认帧的快照，用正确输入重新模拟，一路追帧到当前帧。追帧时不渲染，所以很快。我的实现最大回滚 15 帧，超过就强制同步。"

### Q: 回滚时视觉怎么处理？
> "回滚后物体位置可能跳变。我用了渲染插值——把物体从'预测错误的位置'LERP 到'回滚后正确的位置'，速度设为 10/s，人眼几乎感知不到。格斗游戏不用插值因为画面是离散的（帧冻结效果自然掩盖了跳变）。"

### Q: 你的 RUDP 为什么不用 KCP？
> "KCP 更成熟但也更重——它有完整的 ARQ 状态机。我的场景只需要'输入包可靠送达'，所以自己实现了极简 RUDP：12 字节 header、序列号 + ACK bitfield + 超时重传。一个 ACK 能确认 33 个包。如果以后需要更复杂的可靠传输会考虑换 KCP。"

### Q: 怎么保证帧同步的确定性？
> "三个层面：①物理层面——碰撞按 EntityId 排序、纯函数模拟无隐藏状态；②数学层面——理想方案是定点数，我目前用 float+哈希校验做验证；③逻辑层面——不用基于真实时间的 Timer，全部基于帧步进。"

### Q: UE 的网络同步怎么做的？
> "UE 默认用状态同步——服务端是权威，通过 Replicate 同步 Actor 属性到客户端。网络层用自研 RUDP（基于 UDP），特点是 Nak 驱动重传而不是超时重传，用 256 位 History 追踪每个包的确认状态。还有两层保序：Packet 级别的 PacketOrderCache 和 Channel 级别的 InRec 队列。"

## 八、GGPO 深度架构（DeepWiki 源码分析）

### 七大核心组件

```
游戏应用层
    ↕ GGPOSessionCallbacks（save/load/advance/on_event）
GGPO SDK 层
    ├── P2P Backend（玩家同步）
    ├── Sync Test Backend（确定性验证，调试用）
    ├── Spectator Backend（观战管理）
    ├── Sync Object（状态历史 + 回滚管理）
    ├── Input Queue Object（输入追踪 + 预测）
    ├── TimeSync Object（墙钟时间差近似）
    └── UDP Protocol Object（输入压缩 + 可靠 UDP）
```

### 游戏集成接口（开发者必须实现）

| 回调 | 何时被调用 | 作用 |
|------|-----------|------|
| `save_game_state()` | 每帧 | 保存完整游戏状态快照 |
| `load_game_state()` | 回滚时 | 恢复到之前的状态 |
| `advance_frame()` | 正常推进 + 回滚重放 | 用给定输入模拟一帧 |
| `on_event()` | 网络事件 | 连接/断开/同步通知 |
| `free_buffer()` | 状态过期 | 释放快照缓冲 |

### GGPO 典型游戏循环

```
① ggpo_idle()              → 处理网络消息
② 读取本地输入
③ ggpo_add_local_input()   → 提交本地输入
④ ggpo_synchronize_input() → 获取所有玩家输入（含预测）
⑤ 用输入推进游戏逻辑
⑥ ggpo_advance_frame()     → 通知帧完成
※ 预测错误时 GGPO 自动触发 load → advance(多次) 的回滚
```

### 你的 PredictionEngine vs GGPO

| | GGPO | 你的 PredictionEngine |
|---|---|---|
| 架构 | 回调驱动（游戏实现接口） | 主动调用（Bridge 调度） |
| 状态管理 | Sync Object 内部管理 | SnapshotManager 独立管理 |
| 回滚触发 | 自动（内部检测） | 手动（OnServerInputReceived） |
| 适用性 | P2P 格斗/动作 | C/S 帧同步 |

**面试话术**：
> "GGPO 是回调驱动的——游戏实现 save/load/advance 三个接口，GGPO 内部管理状态历史和回滚时机。我的实现是主动调用的——SimulationBridge 负责调度，PredictionEngine 负责预测和回滚判定。架构不同但核心算法一致：预测→快照→比对→回滚→重放。"

## 九、GGST（罪恶装备 Strive）的回滚网络

### 从 Delay-based 到 Rollback 的转变

GGST 之前的系列（Xrd）用的是**延迟型网络**（Input Delay），GGST 切换为回滚：

| | Xrd（延迟型） | Strive（回滚型） |
|---|---|---|
| 远程输入处理 | 等待到达 | 预测+回滚 |
| 操作手感 | 延迟明显（RTT/2） | 接近本地 |
| 回滚视觉 | 无 | 偶有闪跳 |
| 在线匹配体验 | 海外差 | 大幅改善 |

### 格斗游戏回滚的特殊性

1. **输入简单**：方向+6 按钮，预测准确率极高（短时间内输入不变概率 >80%）
2. **帧冻结天然掩盖回滚**：格斗游戏的 hit-stop（打击硬直）让回滚后的画面跳变不明显
3. **P2P 架构**：只有 2 个玩家，无服务端，延迟 = 单程而非往返
4. **严格确定性**：格斗游戏天然要求帧精确——同一帧的输入必须在同一帧处理

### Rollback 的隐藏成本

- 每帧需要 save/load 完整游戏状态 → **序列化开销**
- 回滚时需要快速重新模拟多帧 → **CPU 峰值**
- 视觉修正（"rollback artifact"）→ **画面闪跳**
- 音效处理困难 → 回滚时音效已经播放了，不能"撤回"

**面试话术**：
> "格斗游戏的回滚有天然优势——输入简单（方向+按钮）所以预测准确率高，hit-stop 的硬直帧自然掩盖了回滚闪跳。GGST 的成功证明了即使是 3D 格斗游戏也能用回滚网络。隐藏成本是每帧的状态序列化开销和回滚时的 CPU 峰值。"

## 十、永劫无间的同步方案分析

### 架构推测（基于社区分析和游戏表现）

永劫无间是**大逃杀 + 近战动作**，60 人同服，同步挑战极大：

| 特征 | 分析 |
|------|------|
| **基本架构** | 状态同步为主（服务端权威） |
| **振刀判定** | 服务端判定，振刀窗口约 80ms |
| **霸体/霸刀** | 状态机在服务端维护，客户端表现层跟随 |
| **延迟感知** | 120ms+ 延迟时振刀明显不跟手 |
| **本地预测** | 移动和部分动作有客户端预测 |

### 动作游戏同步的核心矛盾

```
60 人大逃杀 → 必须状态同步（帧同步不可能支撑 60 人）
近战动作 → 需要低延迟（振刀 80ms 窗口）
    ↓
矛盾：状态同步的延迟 vs 动作游戏的操作精度要求
    ↓
永劫的妥协：
  - 移动：客户端预测 + 服务端校正（低延迟感）
  - 近战判定：纯服务端（防作弊但有延迟）
  - 远程攻击：延迟补偿（射击型技能）
```

### 面试话术

> "永劫无间是 60 人大逃杀+近战动作，用状态同步是必然选择——帧同步撑不了 60 人。核心矛盾是状态同步的延迟 vs 振刀 80ms 判定窗口。它的做法是移动用客户端预测保手感，近战判定纯服务端保公平，远程技能用延迟补偿。代价是高延迟时振刀体验差。"

## 十一、Gaffer On Games 经典文章体系

Glenn Fiedler 的文章形成了一条完整的游戏网络学习路径：

### 文章索引

| 文章 | 核心内容 | 面试价值 |
|------|---------|---------|
| **UDP vs TCP** | 游戏应选 UDP——TCP 的可靠性机制引入不可接受的延迟 | ⭐⭐⭐⭐⭐ |
| **Sending and Receiving Packets** | UDP 收发包实操 | ⭐⭐ |
| **Virtual Connection over UDP** | 在无连接的 UDP 上建立虚拟连接 | ⭐⭐⭐ |
| **Reliability and Congestion Avoidance** | 在 UDP 上定制轻量可靠传输 | ⭐⭐⭐⭐ |
| **What Every Programmer Needs To Know** | 游戏网络总览（P2P→C/S→帧同步→状态同步） | ⭐⭐⭐⭐⭐ |
| **Floating Point Determinism** | 浮点确定性——帧同步的生死线 | ⭐⭐⭐⭐⭐ |
| **Fix Your Timestep** | 固定时间步长 = 物理稳定+确定性的基石 | ⭐⭐⭐⭐⭐ |

### Fix Your Timestep 核心（你项目直接相关）

```
渲染循环（帧率可变）
    每帧产生 frameTime → 喂入 accumulator
    
    物理模拟循环（dt 固定）
        while (accumulator >= dt):
            previousState = currentState
            integrate(currentState, t, dt)
            accumulator -= dt; t += dt
    
    alpha = accumulator / dt
    renderState = lerp(previousState, currentState, alpha)
    render(renderState)
```

**三个原因必须固定 dt**：
1. 数值稳定性——可变 dt 导致弹簧爆炸/穿墙
2. 确定性可复现——帧同步的基石
3. 一致的游戏体验——30fps 和 144fps 物理行为一致

**面试话术**：
> "Fix Your Timestep 是 Gaffer On Games 的经典文章。核心思想是物理用固定步长保证稳定和确定性，渲染用可变帧率保证流畅，两者通过累加器 + 状态插值解耦。我的帧同步项目用的就是这个方案——SimulationWorld 以固定 33ms 步长运行，渲染层做插值。"

## 十二、网易雷火 Jerish 网络同步三部曲

网易游戏雷火的 Jerish 写了上中下三篇系统文章，被广泛引用：

### 文章结构

| 篇 | 主题 | 核心内容 |
|----|------|---------|
| **上** | 帧同步 | Lockstep 起源→Bucket Sync→乐观帧锁步→确定性→王者荣耀方案 |
| **中** | 状态同步 | Quake 快照同步→属性同步→客户端预测→延迟补偿→插值/外推→守望先锋 |
| **下** | 方案选型 | 混合方案→各游戏类型适合什么→优化手段汇总 |

### Jerish 的关键观点

1. **帧同步不是"帧"同步**——名字有误导性，核心是"输入同步+确定性模拟"
2. **状态同步不是"简单"同步**——客户端预测+延迟补偿+插值的工程复杂度不低于帧同步
3. **守望先锋是最成功的混合案例**——ECS 架构 + 状态同步 + 客户端预测 + 服务端回滚
4. **王者荣耀证明帧同步可以大规模商用**——乐观帧锁步 + 服务端验证 + Hash 校验

### 状态同步的四大优化技术（Jerish 总结）

| 技术 | 解决什么问题 | 代表游戏 |
|------|-------------|---------|
| **客户端预测** | 输入延迟高 | 几乎所有 FPS |
| **延迟补偿** | "我明明打中了"（命中判定） | CS:GO / Overwatch |
| **插值** | 远端玩家移动不平滑 | 所有网络游戏 |
| **外推（Dead Reckoning）** | 降低显示延迟但有误差 | 飞行/赛车模拟 |

## 十三、事件流同步（Event Stream Sync）

### 概念

事件流同步不同步"状态"也不同步"输入"，而是同步"**事件**"：

```
传统状态同步：每帧发送 {position, rotation, health, ...}
事件流同步：只发送 {PlayerMoved, DamageTaken, SkillCast, ...}
```

### 核心思想

```
事件 = 有因果关系的状态变更

事件类型：
├── 确定性事件（MoveCommand → 位置变更）→ 客户端可本地重算
├── 服务端事件（DamageTaken → HP 变更）→ 必须从服务端接收
└── 广播事件（ChatMessage → 显示）→ 不影响游戏逻辑

优势：
├── 带宽极低（只传有变化的事件）
├── 天然支持回放（事件序列就是回放数据）
├── 可审计（每个状态变更都有事件来源）
└── 适合事件驱动架构（ECS + Event Bus）

劣势：
├── 事件丢失 = 状态分歧（需要可靠传输或定期快照校正）
├── 事件顺序必须保证（否则因果关系断裂）
└── 复杂游戏逻辑难以完全事件化
```

### 实际应用

| 游戏类型 | 事件流同步的应用方式 |
|---------|-------------------|
| **卡牌/棋牌** | 纯事件流（出牌/抽牌/效果触发） |
| **MOBA** | 技能释放+伤害结算用事件，移动用状态同步 |
| **RTS** | 命令事件（帧同步的输入本质就是事件） |
| **MMO** | 低频事件（任务完成/物品获得）用事件流，高频数据（位置）用状态 |

### 与帧同步的关系

> **帧同步的"输入"本质就是一种事件流。** 帧同步 = 按帧打包的事件流 + 确定性重放。

**面试话术**：
> "事件流同步是介于帧同步和状态同步之间的思路——不同步完整状态，只同步'发生了什么'。带宽极低且天然支持回放，但对事件可靠性和顺序性要求高。实际上帧同步的输入就是按帧打包的事件流。很多游戏会混合使用——高频数据用状态同步，低频逻辑用事件流。"
