> 收纳"如何与 AI 协作"的元层偏好。新条目按时间倒序追加,旧条目不删除。

---

## 1. 优先级评估必须包含"反馈价值"维度(2026-04-24)

**规则**:**优先级规则不破**——既定的 P0/P1/P2 顺序必须遵循。但允许基于"反馈价值/对下游助力"的明确依据**正式提升某个低优先级项的优先级**,而**不是绕过规则插队**。

**Why**:
- 用户在 harness-governance-v1 讨论中指出:Phase 4(评估账本)被我列为 P2,但本任务自身就是个样本——账本越早上线,样本积累越多,后续 Phase 越早能用数据指导决策。**时间不可逆**,晚做一天就永远丢一天数据。
- 我之前只看"任务本身的优先级",漏掉了"任务对其他任务的助力"这个维度。

**How to apply**:
- 排 Phase / 任务顺序时,除"任务自身重要性"外,加问一个问题:**"早做这个对其他任务有什么不可逆的助力?"**
  - 创造新数据(账本、监控)→ 反馈价值★★★(时间不可逆)
  - 提供下游 schema(矩阵、协议)→ 反馈价值★★★(避免下游反复改)
  - 减损工作量(命名、规范)→ 反馈价值★★(线性损失)
  - 单纯止血(GC、清理)→ 反馈价值★(不阻塞下游)
- 如果某项反馈价值显著高于其当前优先级,**走"正式重排"流程**:在 REQUIREMENTS / Phase 表里更新优先级 + 写明升级依据,而不是"我先做这个吧"绕过规则。
- 升级原则:**创造 > 减损**;**早做受益的项** > **晚做无损的项**。
- 必要时拆分:大 Phase 可以拆出"最小骨架"(P0)+ "完整版"(原 P) 两段,骨架早做,完整版按原优先级。例:Phase 4 拆成 4-A(账本写入骨架,P0)+ 4-B(可视化/reader,P2)。

## 2. AI 应主动记忆 + 主动回复"已记忆"(2026-04-24)

**规则**:用户给出反馈、纠正、偏好、决策时,我应当**主动**:
1. 当场写入 memory(按 CLAUDE.md 铁律的纠正分类规则:风格/方式纠正→feedback,知识纠正→knowledge)
2. 写完后**显式回复"已记忆到 `<文件名>` 的 `<章节>`"**——让用户知道已落地,无需追问

**Why**:
- 用户原话:"我希望我反馈后你能直接记忆然后给我一个回复说这一点已经记忆到了。而不是需要我手动让你记忆"
- 之前我经常做完事忘记记 memory,或记了不告诉用户,导致用户每次都要追加一句"记一下"。

**How to apply**:
- 触发条件(以下任一即触发主动记忆):
  - 用户用"我希望" / "下次" / "以后都" / "我倾向" / "我喜欢/不喜欢" / "应该这样而不是那样" 表达偏好
  - 用户纠正我的工作方式("不要这样" / "换种方式" / "格式不对")
  - 用户给出元方法论(像本条 §1)
  - 用户在讨论中给出**明确决策**且影响超出当前任务(适用未来场景)
- 不触发主动记忆:
  - 单次任务内的局部决策(如"用方案 B")——属于任务上下文,不是长期偏好
  - 用户在 AskUserQuestion 里点选项——属于一次性选择,不是偏好声明
- 写入位置选择:**优先合并到现有 feedback 文件**(去重,避免文件数膨胀);只在主题确实没有现有文件时才新建。
- 用户也指出:这个能力可能需要他额外调控 agent / 我可能没完美做到——记此条本身就是兜底机制(下次回看本条会触发自检)。

**自检清单**(每轮回复前过一遍):
- [ ] 本轮用户是否给了反馈/纠正/元偏好?
- [ ] 如是,是否已 Edit 写入对应 feedback 文件?
- [ ] 是否在回复中明确告知"已记忆到 X"?

## 4. 多 Phase 任务必须先建终态架构,再渐进式落地详细设计(2026-04-24)

**规则**:任务包含 ≥3 个 Phase / 跨多个子系统 / 涉及组件交互时,DESIGN 文档**必须**先有一节"整体架构思想 + 终态愿景",然后各 Phase 详细设计才能延后。**不能用"待启动"占位打发后续 Phase**——那等于"做一个想一个",会导致整体不连贯、Phase 间反复推翻。

**Why**:
- 用户原话(harness-governance-v1 DESIGN 评审):"我希望的是一个大体的规划下先准备好,然后具体情况具体分析,再展开详细的规划。其他的方案可以先不落地,但你得有一个大体的方向,一个整体的架构思想,而不是解决一个问题然后下一个问题又重新思考,设计"
- 我之前的 DESIGN §1 只画了 Phase 间执行依赖(数据流图),没画"终态系统长什么样";§3 直接用"待启动"塞过去——正是用户反对的"递归思考"模式。

**How to apply**:
- DESIGN §1(整体架构)**必须**包含:
  1. **终态愿景**:任务完成后整个系统由哪些层/组件构成,各自职责
  2. **核心数据流 / 控制流**:数据从哪里来、流到哪里、谁消费、谁阻断
  3. **信任边界**:哪些是硬阻断(hooks),哪些是软校验(脚本),哪些是文档约定(靠自觉)
  4. **横切原则**:所有 Phase 共享的设计约束(命名、可观测性、回滚、单一数据源、可测试性等)
  5. **可观测性策略**:运行证据 / 状态聚合 / 结果度量 三层各自的载体
  6. **演进路径**:本期不做但终态需要预留的扩展点 + 触发条件
- DESIGN §N(各 Phase 详细设计):
  - 已启动 Phase → 完整设计(影响清单、步骤、验收、风险、回滚)
  - 未启动 Phase → **不能用"待启动"打发**,至少给:
    - **角色**:该 Phase 在终态架构里扮演哪个组件
    - **方向**:主要技术决策方向(不展开,但点出关键 trade-off)
    - **接口**:与其他 Phase 的输入/输出契约(共享 schema、调用关系)
    - **依赖**:谁是它的前置 / 它阻塞谁

**触发场景**:
- 任务 Phase 数 ≥ 3
- 任务跨多个子系统(harness / skill / hook / script / 文档)
- Phase 间存在共享 schema 或数据通道
- 任务有"演进路径"(本期不做但需预留)

**反例**:
- ❌ DESIGN §1 只画 Phase 执行依赖图(没画终态系统长什么样)
- ❌ DESIGN §3 各 Phase 写"待启动"占位(等于没写)
- ❌ "等做到那个 Phase 再设计"——等于放弃整体架构

## 3. 问决策点前必须先 brief 上下文(2026-04-24)

**规则**:在用 AskUserQuestion 让用户拍板前,**必须先用 1-3 段把"这个决策点是什么需求、为什么需要决策、各选项实际意味着什么"讲清楚**。不能默认用户还记得几轮前讨论过的需求细节,更不能假设用户在脑里持有完整上下文。

**Why**:
- 用户原话(讨论 Phase 0 命名格式时):"目前这个需求是什么?我不知道这是啥需求,让我了解点上下文"
- 我前面把 §10.2 当成既定常识,直接抛出"命名格式三选",用户没法判断——因为他不记得 §10.2 是什么时候提的、为什么要分、当前哪些文件踩了坑。

**How to apply**:
- 提问前的 brief 至少包含:
  1. **起源**:这条需求/决策点是哪轮提的?用户原话或一句话总结
  2. **现状错处**:目前实际状态是什么样、哪些文件/行为违反了期望
  3. **期望目的**:为什么这个决策重要(不只是审美/风格,要讲到行为/结果层面)
  4. **各选项的实际后果**:不只是描述,要带例子(文件名长什么样、操作流程会怎么变)
- AskUserQuestion 的 option 描述里塞太多上下文会被截断——所以**主消息体里必须先铺垫**,option 描述只补差异化决策点。
- 触发场景:
  - 决策点跟 N 轮前的讨论挂钩(用户不一定记得)
  - 用户用"什么是 X" / "为什么要 Y" / "我不知道" 表达困惑
  - 涉及新概念/新约定的首次拍板
