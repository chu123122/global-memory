## 2. 技术风险 — 🟡

**发现**：
- **JSONL 日志无轮转**：DESIGN §3.3 + REQUIREMENTS §5 + SPEC §5 都承认 `~/.claude/logs/control_panel_events.jsonl` 会无限增长，处理方案统一是"后续可加清理或轮转"。但**没有定义触发轮转的阈值**（多少 MB / 多少行 / 保留多少天）。在长期运行 + 每 2 秒轮询的场景下，文件膨胀后每次 `read new JSONL lines` 的 seek/解析成本会线性升高。这是已知风险但缺失退出条件。
- **2 秒轮询 × 文件读取**：DESIGN §3.3 说"读 new JSONL lines"，但没说明实现是否记录 last offset / last inode。如果是每次重读全文件，到 N MB 后会有 GUI 卡顿。文档未声明实现策略，需要交叉验证 `control_panel.py`（本次未读取，无法判定，**信息不足**）。
- **跨平台滚轮**：DESIGN §4.3 描述了 Windows/macOS/Linux 滚轮分歧处理（`event.delta` vs Button-4/5），但 V8 验收标准列表里没有"跨平台滚轮"——而 V3 仅说"鼠标滚轮可用"。考虑到用户主环境是 Windows（CLAUDE.md 显示 win32），V1 实际只能验收 Windows 路径，Linux/macOS 的兼容性是声明而非验证。
- **DESIGN §3.0 表格末行 "非 JSON / 脚本失败 → 默认是否展示命令行：是"** 与 §1.1 "原始命令行是调试层，不是主界面" 在脚本失败这一边界情况下产生张力——失败时默认展开调试输出是合理的，但产品原则没显式声明这一例外。
- **smoke import 兼容性**：DESIGN §4.2 末尾自己点出 "`smoke_test.py` 的直接文件 import 方式暴露了 `control_panel_model.py` 导入兼容问题"。HANDOFF "已完成"列出"模型测试已纳入 smoke"，"当前验证结果" `25 PASS / 0 WARN / 0 FAIL / 3 SKIP`——0 FAIL 与 DESIGN 里"需要修复"的描述存在轻微矛盾，需澄清 3 个 SKIP 是否就是该 import 兼容问题。

**建议**：
- DESIGN §3.3 补充"事件 JSONL 轮转触发条件"：例如文件 > 5 MB 或 > 10000 行时滚动到 `.1` 后缀，保留最近 3 份。给"后续演进"一个可触发的退出阈值。
- DESIGN 增加一段实现约束："control_panel.py 必须维护 last_offset，避免每次轮询全量重读 JSONL"。如果实现已经这么做，把它固化到设计文档；如果没做，记入风险表。
- DESIGN §4.3 表格中"跨平台滚轮"加注 "V1 仅在 Windows 上验收，Linux/macOS 为兼容性声明非验证"。
- 在 DESIGN §3.0 数据提炼契约下方加一句："脚本失败为唯一默认展开调试输出的例外。" 消除 §1.1 与表格的张力。
- HANDOFF "当前验证结果" 列出 smoke 的 3 个 SKIP 具体是哪几条，确认与 DESIGN §4.2 自陈的导入兼容问题是否已解决。

## 3. 替代方案评估 — 🟡

**发现**：
- **Tkinter vs PySide/Web** 的选择只在 HANDOFF 决策表里有"当前环境无额外依赖，稳定优先"一句话，REQUIREMENTS §6 / DESIGN §7 把 PySide/Web 列为"后续演进"，但**没有写明触发迁移的客观条件**（用户量？UI 复杂度阈值？性能瓶颈？）。属于"先做最简版，将来再说"，缺退出标准。
- **文件型事件总线 vs HTTP/WebSocket** 的 trade-off 在 REQUIREMENTS §5、DESIGN §3.3、`panel_api.py:5` 注释里都有，理由清晰（无端口、无服务、AI/脚本都能调用，代价是 2 秒延迟）。这是文档中**做得最好的一项**替代方案评估。
- **数据提炼层（V1.2 模型层）vs 直接在 GUI 里判断**：DESIGN §3.0 + §4.3 V1.2 增强部分讲了为什么抽出来（可测试性 + UI 只渲染），但**没有讲为什么 V1 一开始没这么做**——V1.2 是反应式重构而非前瞻设计。这点对未来的设计决策有教学意义，建议在 DESIGN 或 dev-log 补一段"为什么需要 V1.2 重构"。
- **AI execute 拒绝**：决策很坚决，但没讨论"是否应该走白名单 execute（例如只允许某些命令）"作为中间方案。当前是二元 reject，可能在后续被反复挑战，提前写明"为什么不要白名单"会减少未来争论。

**建议**：
- DESIGN §7 / REQUIREMENTS §6 的每条"后续演进点"加一行"触发条件"。例如 `本地 HTTP API：当出现 ≥1 个无法走 JSONL 的真实外部消费者时启动`、`PySide6/Web UI：当 V1.2 结论面板的渲染需求超出 Tkinter Canvas 能力时启动`。
- DESIGN §5 安全边界表后增加一段 "V1 拒绝 execute 的两个 alternative 与拒绝理由：①白名单 execute（拒绝原因：白名单维护成本高于人类点确认）；②人类在 GUI 里二次确认 execute（拒绝原因：当前 GUI 没有可信 sandbox 显示影响范围）。"
- dev-log/phase1.md 增加"V1→V1.1→V1.2 的演进根因"小节，把"V1 把判断写在 GUI 里 → 测不动 → V1.2 抽模型层"的故事固化为团队记忆。
