# HARNESS_REVIEW 模板 — 体系验证清单

> 位置：~/.claude/skills-repo/_bootstrap/templates/HARNESS_REVIEW.md
> 用途：跑完 SPEC→WORKFLOW 流程后，对着这 10 个问题逐项检查，判断设计拆得对不对
> 核心原则：卡住的地方就是设计有问题的地方。不看"文档写得好不好"，看"跑的过程中哪些环节卡了"

---

## 使用方式

1. 每次使用 Harness 体系（SPEC→WORKFLOW→代码→交付）完成一个任务后填写
2. 放在项目的 `docs/HARNESS_REVIEW.md`
3. 每个问题写 1-2 句话回答，5 分钟就能完成
4. 积累 3-5 次后回顾，找到反复出现的问题 → 改进模板

## 与其他模板的关系

```
SPEC（做之前）→ WORKFLOW（做的过程中）→ HARNESS_REVIEW（做完之后）→ HANDOFF（交接时）
```

---

## 模板

```markdown
# [项目名] · Harness 体系验证

> 填写时间：[YYYY-MM-DD]
> 任务概述：[一句话描述]
> 使用的流程：[SPEC → 设计文档 → Phase 1-N → ...]

---

## 关于 SPEC（任务启动前的验收契约）

### Q1：写 SPEC 的时候，有没有觉得"这个填起来好烦"？

> [如果觉得烦，记录哪些字段多余。那些就是需要精简的]

### Q2：SPEC 写完后，AI 在后续工作中有没有引用过 SPEC 里的内容？

> [有引用 = SPEC 有效；没引用 = SPEC 变成了摆设]

---

## 关于 WORKFLOW（阶段流转）

### Q3：实际做的时候，有没有按 WORKFLOW 定义的阶段走？

> [如果有偏差，记录实际走的流程是什么——那个才是真正的 WORKFLOW]

### Q4：有没有某个阶段觉得"这一步没必要，直接跳到下一步更快"？

> [有 = 那个阶段可能是过度设计]

---

## 关于双 Agent

### Q5：这次用的是哪个 Agent？过程中有没有切换到另一个 Agent 的需求？

> [有切换冲动 = 双 Agent 边界模糊的地方]

---

## 关于记忆系统

### Q6：过程中有没有产生"这个应该记下来以后用"的信息？

> [有的话：触发了 [MEMORY_UPDATE] 吗？格式好用吗？]
> [没有的话：可能任务类型不适合产生记忆，正常]

---

## 关于三层金字塔

### Q7：让 AI 做的事情里，有没有哪步是"每次都一样的机械操作"？

> [有 = 那个步骤应该下沉为 Script 或 Skill]

---

## 关于产出质量

### Q8：AI 的产出，直接能用还是需要大改？

> [需要改的话：格式问题 → 缺 Rule；内容问题 → 缺 Skill/示例；理解问题 → 缺上下文]

### Q9：AI 有没有做出"我明确不想要的行为"？

> [有 = 应该成为一条新的 Rule]

---

## 总结判定

### Q10：如果明天再做一个类似任务，会怎么改流程？

> [写下来。这就是你的下一轮迭代。]

---

## 使用记录

| 日期 | 任务 | 主要发现 |
|------|------|---------|
| | | |
```

## 好的 HARNESS_REVIEW 的特征

1. **诚实** — 不是汇报成绩，是找问题。"一切都好"不是好答案
2. **具体** — "SPEC 中的排除范围字段被 AI 引用了 2 次"比"SPEC 有用"有价值得多
3. **可操作** — 每个发现都应该能转化为一个具体的模板修改
4. **积累性** — "使用记录"表随使用次数增长，3-5 次后就能看到模式

## 从 Review 到改进的路径

```
HARNESS_REVIEW 发现问题
    ↓
分类：SPEC 问题 / WORKFLOW 问题 / Rule 问题 / Skill 问题
    ↓
修改对应模板（_bootstrap/templates/ 下的文件）
    ↓
下次使用时验证改进是否有效
    ↓
再填一次 HARNESS_REVIEW
```

这就是 Harness 体系的"进化"闭环。
