# 人类向文档写作风格规则

> 适用：`REQUIREMENTS.md` / `DESIGN.md`（决策 6 限定）
> 不适用：`SPEC.md` / `HANDOFF.md` / 记忆 / 复盘
> 参考样例：`style-refs/` 目录下用户认可的样本

---

## 1. 总体定位

**写给同行工程师 / 主管 / mentor 看，不是写给 AI 也不是写给非技术人员**。允许使用专业术语（Binder / Ticker / IPC / MAGT / Pimpl 不翻译），但要让一个不熟悉本项目的工程师能在 5 分钟内看懂"做什么、为什么、怎么验"。

---

## 2. 该做（Do）

### 2.1 开头直接

第 1 段 1-3 句把"是什么 / 给谁用 / 解决什么"说清。**不写**"## 1. 业务背景（Why）"那种英文括号注释式标题。

✅ 示例（来自 xd-adp 需求分析「业务背景」）：

> 需要一个插件提供手机底层信息，供业务层做画质选择，从而优化玩家游玩体验

### 2.2 数字尽量具体

"1300 行" / "30-100 ms" / "6 次/秒" / "216 行大函数"，不写"较多 / 较慢 / 较长"。

### 2.3 优先级直标 P0/P1/P2

后面跟一句括号说原因即可：`P0（影响玩家）` / `P1（影响可维护性）` / `P2（清理）`。

### 2.4 代码块带文件:行号注释

C++ / Python / Lua 代码块第一行用 `// 文件路径:行号  一句中文描述`。截关键行，不复制整个函数。

✅ 示例：

```cpp
// MediaTekPerfMetricesMonitor.cpp:124-176  MAGT 初始化（启动期同步）
SupportedVersion.value = queryServiceVersion(0);
EMTKResult::EResult InitResult = (EMTKResult::EResult)init(...);
```

### 2.5 表格用于"枚举 + 对比"

至少 3 列才用表。常见模式：
- **平台/方案对比表**：列 `平台 / 实现 / 行数 / 状态 / 备注`
- **风险表**：列 `风险 / 概率 / 影响 / 缓解`
- **方案选型表**：列 `方案 / 评价` + 末尾 ✅ **本期选用** + 一句理由
- **阶段表**：列 `阶段 / 内容 / 目的 / 本期?`，用 `✅ / ❌ 后续` 标边界
- **验收表**：列 `# / 验收项 / 标准 / 验证方法`

状态用 emoji：`✅` 真干活 / `⚠️` 半废弃 / `❌` 不要 / `🚧` 待办 / `⚪` unknown。

### 2.6 ASCII 时序图 / 调用链

调用关系、时序、阶段流转用 ASCII 图（`├─` `└─` `▼` `→`），右侧加 `【显式】 / 【UE 回调】 / 【懒初始化】` 标注触发方式。

✅ 示例（来自 xd-adp 设计「调用时序图」）：

```
[T0  PreDefault] StartupModule()                       【显式】
                 ├─ 设备查询/打日志/诊断
                 ├─ 条件注册 CSV Sampler Ticker
                 └─ 条件创建 UMG Widget
                     └─ Widget::NativeConstruct()      【UE 回调】
                         └─ UMonitorData::Get() 首次  → UMonitorData 单例初始化
```

### 2.7 风险章节用「现方案 → 代价 → 新方案」对比

不只列风险标题，要把"现状的代价"和"新方案怎么解决"放并排。

✅ 示例（来自 xd-adp 设计「风险」）：

> 现方案靠「懒加载到第一次 Query」——代价是首次 Query 那一帧 30-100ms 卡顿, 且卡顿位置随机
> 新方案靠「OnPostEngineInit 主动起异步任务」——主线程零阻塞, 业务侧用 OnMonitorReady 委托接收就绪事件

### 2.8 承认不确定

未知就标"⚠️ 待验证假设"独立列出，估算就写"估算耗时"+"实际需真机用 X 实测"。

退化方案给具体级别（L1 完整 / L2 退化 / L3 完全回滚），不只说"如果失败就回滚"。

### 2.9 嵌入式自注释允许

行内可以加编辑批注：`（问题，下面单列）` / `（已确定，xxx）` / `**注：本次只修复"启动初始化阶段"放子线程**`。

### 2.10 章节长度可以 wildly 不均

某个小节只有标题没内容是 OK 的（占位待填，比凑"暂无"诚实）。但**最终交付前这种空章节要么填要么删**。

### 2.11 重构内容用人话总结

✅ 示例（来自 xd-adp 需求分析「范围与验收」）：

> **初始化放到子线程，把代码理顺，把测试补上**

不要写"# 5. 范围与验收（Scope & Acceptance）"。

---

## 3. 不该做（Don't）

### 3.1 结构癌

❌ 不要把每段都拆成表格。"业务背景"是一段话，不是 4 列表。

### 3.2 占位符综合症

❌ 不要照抄模板里的 `[一句话说清要交付什么]` 或 `<!-- 现状是什么？谁在痛？痛多久了？ -->`。**模板的 HTML 注释行必须删掉再写正文**。

### 3.3 工程黑话堆砌

❌ 谨慎使用：`trade-off` / `schema` / `metadata` / `business value` / `scope` / `derive` / `pipeline`（除非是技术专有名词如 "asset pipeline"）。
✅ 替代：`权衡` / `数据结构` / `范围` / `派生` / `流水线`。

技术专名（Binder / Ticker / Pimpl / RHI / Slate / UMG）保留英文。

### 3.4 模板章节强迫症

❌ 不要为了凑齐模板章节写"暂无"或"详见 X"。**没有内容就删除该章节**。

### 3.5 中性 AI 腔

❌ 反例（AI 默认风格）：

> 本次重构旨在优化系统的初始化流程，通过将耗时操作迁移至子线程，从而提升整体性能表现，并改善用户体验。

✅ 改写：

> 启动期主线程被 50-200ms 的 init 阻塞。把这一坨挪到子线程，主线程零阻塞。

### 3.6 综述癌

❌ 不要在每段末尾写"综上所述 / 总结 / 由此可见"。

### 3.7 装作什么都已经定了

❌ 不要写"经过深入调研，我们决定采用方案 X"——除非真的调研过。
✅ 用"⚠️ 待验证假设" / "估算" / "退化方案 L2" 诚实标注不确定。

## 4. 排版细节

| 项 | 规则 |
|---|---|
| 标题 | `#` `##` `###` `####`，最深 4 级 |
| 引用块 `>` | 用于章节定位说明、警告、节选样例 |
| 加粗 `**` | 用于关键词、强调结论、表格内重点 |
| 列表 `-` | 用于真正的并列项，不超过 7 项；超过 7 项考虑改表格 |
| 行内代码 | 文件名 / 函数名 / CVar / 类型 / 标识符必须用反引号 |
| 分隔符 `---` | 仅用于章节边界，不滥用 |
| Emoji | 仅状态标记（✅⚠️❌🚧⚪🎯📋🛠️👉），正文里不撒花 |

---

## 5. 反 AI 腔自检清单

写完后过一遍，命中任意一条就改：

- [ ] 出现"业务价值 / 商业价值 / business value"段落但没有具体数字 → 删
- [ ] 表格只有 2 列且每行内容是完整句子 → 改成段落
- [ ] 章节内容是 `<!-- ... -->` 占位符或"暂无" → 删整个章节
- [ ] 有"综上所述 / 总结 / 由此可见 / 整体而言" → 删
- [ ] 第一段超过 3 句话还没说清做什么 → 重写
- [ ] 用了 `[占位文本]` 没替换 → 替换或删
- [ ] 优先级写"高/中/低"而不是 P0/P1/P2 → 改
- [ ] 风险只列风险不列缓解 → 补
- [ ] 方案对比没说"本期选哪个 + 为什么" → 补

## 7. 元规则

- 本文档自身也按本规则写——**如果读起来像 AI 套模板，那这份规则就失败了**
- 规则可以演化：用户每次说"这段不像人写的"→ 提取规则增量到「该做」/「不该做」章节
- 不强求 100% 命中样例风格——样例是参考下限，允许在保持口吻一致的前提下根据当前任务调整
