## 2. 技术风险 — 🟡

**发现**：
- **JSONL 读取竞争未处理**。设计 §3 说"QTimer 2s 轮询，只读增量（用 last_offset）"，但 `panel_api.py append_event()` 当前是裸 `f.write(json.dumps(...) + "\n")` —— **无锁、无原子性保证**（harness-governance-v1 设计文档第 348 行明确写了这一点）。在 Windows 下 panel_api 写一半时 v2 读到 partial line 会 `json.loads` 抛异常。设计完全没提这个风险，缓解方案也没列。outcome 通道（Phase 4-A）走的是 `_atomic_append_jsonl`，没问题；但 `control_panel_events.jsonl` 通道仍是裸 append。
- **轮询频率"一刀切 2s"对所有 4 个通道是粗糙的**。其中 `git status` 走 `subprocess.run(["git", "status"])`，在 Windows + D:/global-memory 下首次可能 200-800ms（依赖 git index 大小），每 2s 一次会拖累 UI 线程响应；事件 jsonl 的增量读则是毫秒级。建议至少把 git status 拉成独立 QTimer（5s 或 10s）+ QThread 异步执行，或纳入 §7.5 启动性能小节专门评估。
- **§7.5 启动预算 1.5s 与 §8.2 PyInstaller --onefile "启动慢 1-2s" 自相矛盾**。--onefile 模式 PyInstaller 要先解包到临时目录再 import PySide6，PySide6 自身首次 import 实测就 400-700ms，叠加解包开销冷启 3-5s 是正常水位。如果 V1 验收要走 .exe 形态，预算需要重定为 3-5s；如果走 .bat 直跑，--onefile 路径可以推迟到打包 Phase。
- **PyQtDarkTheme 维护风险被低估**。pip 包名 `pyqtdarktheme`，import 名 `qdarktheme`，作者从 2023 年下半年起 release 节奏明显放缓（最后一版是 2.x）。需求 §6 风险表只提了"PySide 7.x 升级时第三方滞后"，但更现实的风险是"PyQtDarkTheme 停止维护，PySide6 6.7+ 出 deprecated API 时无人修"。建议明确"如果 PyQtDarkTheme 失维，回退方案是手写极简 QSS 或切 qdarkstyle"。
- **qtawesome 图标主题适配的实际表现**：设计 §7.4 写"qtawesome 默认随 palette 取色，深色主题自动反色"——这个说法不完全准确。qtawesome 默认色是创建 icon 时锁定的，主题切换时已创建的 QIcon 不会自动重绘。如果走运行时切主题（V7 要求），需要在 ThemeManager.theme_changed 信号里重建所有 tab 图标。设计 §7.2 信号清单没体现这一点。
- **跨平台风险被需求 §6 一笔带过**。本任务环境是 Windows + WSL，但设计 §7.6 直接"沿用 v1 的 `_lib.is_windows()`"——v1 是 Tkinter，PySide6 在 WSLg 下的 Qt platform plugin 加载、字体 fallback、HiDPI 缩放都是新坑。建议 Phase 0 spike 单独覆盖 WSLg 启动验证。
- **接口契约对外部任务的耦合**：设计 §5 列了 4 项依赖 harness-governance-v1 的产物（reader / RULE_ENFORCEMENT_MATRIX / harness_status / outcome schema），但 §5 末尾只说"渐进推进"——缺少"如果 4-B 长期不就绪，v2 哪些页签退化为 placeholder"的最小可用集定义。需求 §5 V4 说"7 页签内容与 v1 等价"，但 v1 没有 outcome / 规则矩阵页签，二者在"账本"页范围上其实有 gap。

**建议**：
- 把"JSONL 半行读取容错"作为 polling.py 的硬要求：try/except json.JSONDecodeError 时回退 last_offset 不前进，等下一轮重读。设计 §7（polling.py）补一节"鲁棒性"。
- 拆分轮询：jsonl 类 2s，git status 类 10s + QThread。设计 §3 把"轮询机制选择"小节扩展为表格列各通道频率与执行线程。
- §7.5 启动预算与 §8.2 打包形态对齐：明确"1.5s 是 .bat 形态预算，.exe 形态另立"。
- §7.4 补一句"主题切换时 ThemeManager 触发 icon refresh"，§7.2 信号清单加 `theme_changed → tab_icon_refresh`。

## 3. 替代方案评估 — 🟡

**发现**：
- 5 选项对比表（需求 §3）维度清晰：滚动/观感/体积/兼容/边界违反。否决 Web UI 的依据（违反 v1 §3.2 + 产品定位漂移）成立。否决 CustomTkinter 的依据（"内核同 Tkinter"）也对——CustomTkinter 是 Tkinter 的 themed wrapper，滚动根问题没解。
- 选 PySide6 vs PyQt6 这一层**没在文档里出现**。两者 API 99% 一致，区别在 license（PySide6 LGPL / PyQt6 GPL or 商业）和 Python 类型 stub 质量（PySide6 自带 .pyi，PyQt6 略差）。需求 §6 风险表提到"商业 LGPL 协议"——这个表述不严谨，PySide6 是 LGPL，PyQt6 才是 GPL/商业双授权。建议用一行说明"选 PySide6 over PyQt6 的理由（LGPL + 官方 Qt 公司维护 + 类型 stub）"。
- 轮询 vs QFileSystemWatcher 的选择（设计 §3）trade-off 充分：列了延迟可接受、watcher 跨平台坑、未来可切换的退路。✅
- widget 树搭建：纯 Python vs Qt Designer（§7.1）trade-off 也充分，Designer 在本场景的收益条件被准确否决。✅
- 信号槽风格：lambda vs @Slot 混合策略（§7.2）合理。但**没讨论第三种**——Qt 5+ 的 `@QtCore.Signal` 自定义信号 vs 直接用 Python callback。考虑到要跨文件传 dict（polling → views），用 Qt Signal 比 Python 回调好（自带跨线程 queued connection 安全），现设计已经隐含选了 Qt Signal，但理由没写。
- 主题：PyQtDarkTheme vs qt-material vs qdarkstyle vs 手写 QSS 的对比，设计 §7.3 只在"不做"段落点了名，没解释为什么 PyQtDarkTheme 优于 qt-material（后者更花哨、Material Design 风格、社区活跃度更高）。
- 打包：PyInstaller vs Nuitka vs cx_Freeze 的对比也只在体积瘦身段提了一句"后续可选 Nuitka"。Nuitka 对 PySide6 体积优势其实可观（30-50%），如果需求 §6 把"体积膨胀"列为风险，应在选型阶段做对比而不是事后补救。

**建议**：
- §3（选型表）补 "PySide6 vs PyQt6" 一行，§6 风险表把"LGPL"措辞修正。
- §7.3 补一句 "选 PyQtDarkTheme over qt-material：更克制、不过度 Material 化，符合工业控制面板调性"——或承认无强偏好、按试装效果决定。
- §8.2 PyInstaller 选型理由补一句"vs Nuitka：本期优先生态成熟度，体积优化推迟到 Phase 5+"。

## 4. 可测试性 / 可维护性 — 🟢

**发现**：
- "不写 GUI 自动化测试"决策合理。pytest-qt 对 7 页签个人项目 ROI 确实低，且 V1-V7 都是交互级验收，自动化覆盖率会很低。✅
- 但 model 层（已经 v1 解耦好）**仍然可以也应该写单测**——设计文档没强调这一点。`summarize_*` 系列是纯函数 dict→dict，写 5-10 个 case 成本极低、对 V4"内容等价"是关键回归保险。建议设计 §6"不做"那一段把"不做 GUI 自动化测试"改成"不做 GUI 自动化测试，但 model 层 summarize_* 函数应有 pytest 单测（已有/待补）"。
- V1-V7 验证方法："实机打开 / 实机滚动 / 对比截图 / 手动测 / 实机切换"——可重复性弱。建议在每条验收下补一个 1-2 行的"复现脚本"：例如 V6 应给出"`python harness/panel_api.py notify --level info --title test --message hello` 后窗口事件页应在 2s 内出现该条"。
- 300 行约束（§7.1）合理可执行，配 `_BasePage` 抽象（标题栏 + QScrollArea + refresh 抽象方法）落地路径清晰。✅
- 代码组织（§7.1 文件树）粒度合适，7 个 view 文件 + 4 个支持文件，grep 友好、git diff 友好。✅
- `theme.py` 的"主题持久化到 `~/.claude/control_panel_pyside.json`"——这个路径与 v1 的 `~/.claude/logs/...` 共享根目录是好事，但应在文档里点出"持久化文件 schema 暂未定义，第一次写时只有 `{theme: "auto"}`，未来加字段需考虑兼容"。
- 文档可维护性：设计 §7.5（启动性能）和 §7.6（跨平台路径）只有一行 placeholder，"Phase 4 / Phase 1 验证"。这是 §1.7 G2"未启动 Phase 轻设计"模式下可接受的，但应在文档头部加"占位章节由对应 Phase 开工时填实"的元说明，避免审查者误判为遗漏。

**建议**：
- §6"不做"小节补 model 层单测的边界（不做 GUI 自动化 ≠ 不做 model 单测）。
- §5 验收标准每条补"复现命令 / 操作步骤"，让 V1-V7 真的可重复。
- §7.5 §7.6 的 placeholder 章节加"待 Phase X 填充"标注，避免被当成漏项。
