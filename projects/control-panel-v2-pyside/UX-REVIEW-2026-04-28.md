# 控制面板 UX 审计报告 · v2.1

> 审计时间：2026-04-28
> 审计 agent：design-reviewer（扮演 control-panel-ux-designer）
> 用户痛点：「目前控制面板不好看，然后难看懂，需要不少时间去理解」
> 优先级：理解成本 ≫ 视觉

---

## Diagnosis（按理解成本由高到低）

### D1. 状态页"当前结论"卡被 token saver 子问题劫持 [核心]
`views/status.py:83-93` 默认渲染 `当前主要问题：未知 / 下一步：刷新状态`，首屏第一秒看到"未知"。
更糟：`_set_decision()` 在 `_update_timeline_card()` 里被覆写（`status.py:367`），结论不来自 git/daemon/doctor 真实健康，而来自一个非常小众的子问题——「token saver / skill audit 是否被 AI 直接调用」。
首屏看到红字"未解决：token saver 还没有运行证据"——99% 用户根本不知道 token saver 是什么，但被红色 verdict 强行劫持注意力。**这是单点最大的"难看懂"来源**。

### D2. "状态" tab 与 "健康" tab IA 边界完全模糊
- 状态页 358 行：Git + Daemon + Doctor + AI 时间线 + 7 按钮
- 健康页 164 行：调 `harness.health.runner` 跑 9 个 check
- doctor 已含 `git_status / check_health / bootstrap_check / verify_prompt_system / verify_docs / smoke_test`，与健康页 9 个 check **概念严重重叠**
- 用户必须在两 tab 之间反复横跳并自己做集合运算才能回答"现在到底有没有事"

### D3. 7 按钮平铺，primary/secondary/dangerous 全部失效 + safety bug
`status.py:67-153` 两段 toolbar 共 7 按钮：
- `[一键修复]` 名义 primary，实际跑 `maintain.py fix` 是**写盘动作**，按 ux-designer.md 应是 Repair 级别需二次确认；**现在点一下立刻跑无任何 confirm**（`status.py:251-265`）
- `[跑 /work pack]` `[跑 Skill audit]` `[记录 outcome]` 是开发者诊断，混在主面板曝光
- 5 个 secondary 全长一样、全有图标、全等权重——视觉上无主次

### D4. 状态页 358 行装 5 个完全不同关注点
(a) 健康结论卡 + (b) Git 卡 + (c) Daemon 卡 + (d) Doctor 6 项明细 + (e) AI 时间线 HTML（含 8 列宽表 + 5 行工具状态 + outcome 子表 + 推荐文案）。
(e) 的 `_update_timeline_card` 一个方法 117 行（`status.py:340-457`），生成的 HTML `<table>` 列宽 8 列——**这是个独立的 dashboard，不是"状态"应承载的**。
副作用：`handle_result(action="status")` 自动级联触发 `_on_timeline_refresh()`（`status.py:279`），每次刷新都强制重跑 `timeline_summary.py --days 7`，让首屏多等一次 IO。

### D5. 视觉层次与状态语义弱
- `_git_label` 渲染 `"dirty=True / ahead=0 / behind=0 / 变更 10"`（`status.py:317-321`）——把 JSON 字段直接拼字符串给人类看，没"判断"
- `decision-headline` 永远只在 `warn/bad` 之间切，**几乎永远是黄/红**，没有 ok 状态分支（`status.py:355-366` 的 if/elif 三个分支默认假设 token saver 没接入 = 都是问题）
- 健康页用 emoji 🔴🟡🔵🟢，状态页用 role 染色——**两套视觉语言在同一窗口共存**

### D6. 文档侧栏 220px 常驻，挤压主区
`doc_sidebar.py:35` 固定 220px，1180px 默认窗口吃 18.6%。
6 个跳转里 4 个低频（FIXLIST/MAINTENANCE/CONTROL_PANEL/conventions）。
变更页：CHANGELOG 跳转和 tab 内容**功能完全重复**。

### D7. 自动刷新闪烁 + 首次切到状态页阻塞跑 2 条命令
- `_BasePage.auto_refresh_interval_sec = 8.0`（`_base.py:27`）
- 健康页 `_render_cards` 全 deleteLater + 重建（`health.py:106-120`）= 一次完整闪烁

## Primary User Flow

### Flow A — 日常体检（80% 场景，预算 5 秒）
1. 双击 → 启动
2. **看默认页第一行结论卡**：绿/黄/红 + 一句话 → **完**
3. 若黄/红 → 点 primary 按钮

**当前失败**：步骤 2 看到的是"未知"或被 token saver 劫持的红字。

### Flow B — 出问题排查（15%，30 秒）
1. 默认页结论 = 红 → 看 reason
2. 点"详情"展开 evidence
3. 点 Repair 按钮（带二次确认）

**当前失败**：doctor 卡片只显示 PASS/WARN/ERROR 计数，不告诉用户"哪一项 ERROR 了"。

### Flow C — 任务上下文切换（5%）
任务 tab → 卡片单击 → 文件管理器开。**这个流程目前最干净，作参考样本保留**。

### 退路方案

- 概览页（rename 自"状态"）：删 AI 时间线 + 5 secondary 按钮，结论卡改 doctor 聚合
- 健康页：保留，概览页结论卡显示一行"健康检查：⚠ 1 警告"

## Interaction Rules

### 按钮层级表（覆盖现有所有按钮）

| 按钮 | 当前位置 | 当前 role | 建议 role | 二次确认 | 备注 |
|---|---|---|---|---|---|
| 一键修复 | 状态页 | primary (`status.py:70`) | **repair** | **是** | fix 是写盘动作，必须改非 primary |
| 刷新 | 状态页 | secondary (`status.py:78`) | secondary | 否 | 保留，归"只读"组 |
| 刷新时间线 | 状态页 | secondary (`status.py:127`) | **删除（迁诊断）** | — | 自动级联即可 |
| 查看最近完整会话 | 状态页 | secondary (`status.py:131`) | **debug**（迁诊断）| 否 | 全 dump 到调试区 |
| 跑 /work pack | 状态页 | secondary (`status.py:137`) | **debug**（迁诊断）| 否 | 开发者脚本 |
| 跑 Skill audit | 状态页 | secondary (`status.py:143`) | **debug**（迁诊断）| 否 | 同上 |
| 记录 outcome | 状态页 | secondary (`status.py:149`) | **debug**（迁诊断）| 是（已有）| 不该占主面板 |
| 健康-刷新 | 健康页 | primary (`health.py:50`) | secondary | 否 | "刷新"语义不该 primary |
| 变更-刷新 | 变更页 | secondary | secondary | 否 | 保留 |
| 任务-刷新 | 任务页 | secondary | secondary | 否 | 保留 |
| 文档侧栏 6 项 | 右侧栏 | secondary | **缩到 2 项**（MEMORY、CHANGELOG）| 否 | 侧栏默认隐藏 |
| **缺失：立即同步** | — | — | **新增 dangerous** | **是（双重）** | 当前面板**无 sync 入口** |

### 刷新行为

- **取消** status → timeline 的级联（`status.py:279`）
- 健康检查冷跑慢，30s throttle 保留，首次切入也走 throttle
- 自动刷新**不重建** widget 树（`health.py:108-114` 的 deleteLater 改为 in-place 文本更新）

### 调试输出

- 默认折叠（已正确）保留
- 出错时 `reveal=True` 自动展开（已正确）保留
- 改进：调试区头部 hint "上次输出：12s 前"，让用户感知有新内容（不强行弹）

### 确认框

- Repair：单次 `QMessageBox.question` + 默认按钮 = Cancel
- Dangerous：先 `QMessageBox.warning` 显示影响范围，再 `QMessageBox.question` 二次确认；二次默认 = Cancel
- 文案要写**具体动作**："要 push N 个 commit 吗"，不能写"确定要继续吗"

### 错误处理

- CLI exit != 0：结论卡 severity → error，reason 截 stderr 第一行，调试区自动展开
- 不在主区显示 traceback / 完整 stderr

## Implementation Notes

1. **优先级 1**：抽 `harness/control_panel_model/overview_verdict.py`，函数 `build_overview_verdict(status_json, doctor_summary, health_signals) -> OverviewVerdict`。所有 severity 合并在 model 层；view 只渲染。

5. **回归保护**：
   - smoke 启动 < 0.5s
   - 4 主题切换无 traceback
