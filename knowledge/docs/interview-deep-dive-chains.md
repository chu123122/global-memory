## 1. enum vs enum class

### Level 1: 基础认知
**面试官**：enum 和 enum class 有什么区别？
**答**：enum class 是 C++11 引入的强类型枚举。主要三个区别：(1) 作用域——enum class 的枚举值必须用 `Color::Red` 访问，不会污染外层命名空间；(2) 类型安全——enum class 不会隐式转换为 int；(3) 可以指定底层类型 `enum class Color : uint8_t`。
**考察**：基本语法认知

### Level 2: 工程实践
**追问**：在 UE 项目中，应该用哪个？有什么坑？
**答**：UE 推荐用 `UENUM()` 标记的 `enum class`，这样反射系统能识别它。但 `UENUM()` 的 enum class 必须是 `uint8` 底层类型才能做 UPROPERTY。如果枚举值超过 255 个需要用 `enum`（非 class）或者拆分。另外 UE 有 `ENUM_CLASS_FLAGS` 宏让 enum class 支持位运算。
**考察**：UE 规范理解

### Level 3: 底层原理
**追问**：为什么 C++ 的 enum 会隐式转换为 int？这背后的设计哲学是什么？
**答**：C++ 继承自 C，C 的 enum 本质上就是一组 int 常量（没有独立类型）。C++ 为了兼容性保留了这个行为。enum class 是 C++11 从 Java/C# 借鉴的"修复"——牺牲一点便利性换来类型安全。这体现了 C++ 的设计哲学：不破坏向后兼容，新特性通过新语法引入。
**考察**：语言设计哲学

## 2. 智能指针 → 循环引用 → weak_ptr

### Level 1: 基础认知
**面试官**：C++ 的三种智能指针分别是什么？什么时候用哪个？
**答**：`unique_ptr` 独占所有权，不可拷贝只能移动——默认首选。`shared_ptr` 共享所有权，引用计数管理——多处持有同一资源时用。`weak_ptr` 弱引用，不增加引用计数——用来打破 shared_ptr 的循环引用。
**考察**：基本概念

### Level 2: 循环引用
**追问**：什么是循环引用？举个具体例子。
**答**：A 的 shared_ptr 指向 B，B 的 shared_ptr 指向 A。两者引用计数永远 ≥1，永远不会释放。典型例子：双向链表节点互相持有 shared_ptr，或者 Parent-Child 关系中双方都持有对方。解决方法：让其中一方（通常是"非拥有方"，比如 Child 指向 Parent）使用 weak_ptr。
**考察**：内存管理理解

### Level 3: 引用计数线程安全
**追问**：shared_ptr 的引用计数是线程安全的吗？拷贝 shared_ptr 呢？
**答**：引用计数本身是 atomic 的——多线程同时拷贝/销毁 shared_ptr 不会导致引用计数错误。但 **shared_ptr 对象本身的读写不是线程安全的**——同一个 shared_ptr 变量在一个线程写另一个线程读，需要加锁。C++20 引入了 `std::atomic<shared_ptr<T>>` 来解决这个问题。
**考察**：并发安全深度

### Level 4: 底层实现
**追问**：shared_ptr 内部的控制块（Control Block）是什么？make_shared 和 new 有什么区别？
**答**：shared_ptr 包含两个指针：一个指向数据，一个指向控制块。控制块包含：strong count、weak count、deleter、allocator。`make_shared` 只做一次内存分配（控制块和数据在同一块内存中），而 `new T` + `shared_ptr<T>(p)` 做两次分配。但 make_shared 的缺点是：弱引用存在时，即使 strong count=0，数据的内存也不能释放（因为控制块还在，而控制块和数据在一起）。
**考察**：底层实现细节

## 3. 虚函数 → 虚表 → 多继承

### Level 1: 基础认知
**面试官**：虚函数是什么？有什么用？
**答**：虚函数实现运行时多态——基类指针调用虚函数时，根据实际对象类型调用对应的实现。编译器通过虚表（vtable）和虚表指针（vptr）实现：每个含虚函数的类有一张虚表，对象头部有一个 vptr 指向它。
**考察**：多态基本原理

### Level 2: 虚表布局
**追问**：虚表在内存中长什么样？虚函数调用的开销是多少？
**答**：虚表是一个函数指针数组，每个虚函数对应一个槽位。调用流程：`obj->vptr -> vtable[slot_index] -> function`，两次间接寻址。开销：一次指针解引用 + 一次函数指针调用。对 CPU 来说，真正的开销不在指针解引用，而是**分支预测失败**——如果多态对象类型经常变化，CPU 预测不准虚函数目标，导致流水线冲刷。
**考察**：性能理解

### Level 3: 多继承虚表
**追问**：多继承时虚表怎么排列？
**答**：每个基类有自己的一个虚表（sub-vtable）。对象内存布局：`[vptr_Base1][Base1 数据][vptr_Base2][Base2 数据][Derived 数据]`。用第二个基类指针调用时，this 指针需要调整偏移（thunk）。这也是为什么 `dynamic_cast` 在多继承中比较慢。
**考察**：内存模型深度

### Level 4: 虚析构函数
**追问**：为什么基类析构函数必须是 virtual 的？不加会怎样？
**答**：如果通过基类指针 delete 一个派生类对象，非虚析构只会调用基类析构——派生类的成员不会被释放，导致内存泄漏。UE 的 UObject 不受此影响（GC 系统知道真实类型），但普通 C++ 类必须遵守这个规则。经验法则：类有虚函数 → 析构函数必须 virtual。
**考察**：资源管理安全

## 4. move 语义 → 右值引用 → 完美转发

### Level 1: 基础认知
**面试官**：什么是 move 语义？解决什么问题？
**答**：move 语义允许"转移"资源所有权而非拷贝——比如 vector 的内部数组指针直接转给新对象，旧对象置空。解决的问题：避免不必要的深拷贝，尤其是临时对象和函数返回值场景。
**考察**：C++11 基本概念

### Level 2: 右值引用
**追问**：左值和右值的区别？T&& 是什么？
**答**：左值有名字、可取地址（`int a = 1; &a` OK）。右值是临时值、不可取地址（`&(a+1)` 错误）。`T&&` 是右值引用——只能绑定到右值（或 std::move 的结果）。`std::move` 不移动任何东西，只是把左值强转为右值引用，**真正的移动发生在移动构造/移动赋值中**。
**考察**：值类别理解

### Level 3: 完美转发
**追问**：std::forward 是什么？什么时候需要用？
**答**：在模板函数中，参数 `T&&` 是万能引用（可以匹配左值和右值）。但传给内部函数时，参数退化为左值。`std::forward<T>(arg)` 恢复参数的原始值类别——左值保持左值，右值保持右值。典型场景：工厂函数、emplace_back 的实现。
**考察**：模板元编程基础

### Level 4: forward 实现原理
**追问**：std::forward 内部怎么实现的？
**答**：利用引用折叠规则。`T` 推导为 `int&` 时（传入左值），`forward<int&>` 返回 `int&`（左值引用）。`T` 推导为 `int` 时（传入右值），`forward<int>` 返回 `int&&`（右值引用）。引用折叠规则：`& + &` = `&`，`& + &&` = `&`，`&& + &` = `&`，`&& + &&` = `&&`。
**考察**：模板元编程深度

### Level 4: 无锁 vs 有锁的选择
**追问**：什么情况下你会选择无锁编程？
**答**：几乎不会主动选无锁。无锁编程的正确性极难验证（ABA、memory order 微妙 bug），调试成本高。只在以下场景考虑：(1) profiling 证明锁竞争是瓶颈；(2) 数据结构极其简单（单个 atomic counter、SPSC 队列）；(3) 有经过验证的无锁库可用（如 Folly、Boost.Lockfree）。游戏引擎中 95% 用锁就够了。

## 6. UE GC → 标记清除 → GC 簇

### Level 1: 基础认知
**面试官**：UE 的 GC 是怎么工作的？
**答**：标记-清除算法。每次 GC：(1) 把所有 UObject 标记为不可达；(2) 从根集合（AddToRoot 对象 + UPROPERTY 引用链 + FGCObject 注册的引用）开始遍历，标记可达对象；(3) 清除不可达对象（分帧增量清除）。
**考察**：GC 基本原理

### Level 2: 与 C++ 析构的关系
**追问**：UObject 的析构函数什么时候被调用？和 GC 是什么关系？
**答**：UObject 不通过 C++ 的 delete 销毁。GC 标记不可达后，依次调用 `ConditionalBeginDestroy()` → `ConditionalFinishDestroy()` → 析构函数 → 释放内存。BeginDestroy 可以做清理逻辑，FinishDestroy 做最终清理。整个过程可以分帧完成——大量对象销毁不会卡一帧。
**考察**：UE 生命周期理解

### Level 3: GC 簇
**追问**：GC 簇是什么？有什么用？
**答**：把一组生命周期一致的对象绑在一起（比如 StaticMesh + 它的 Materials + LOD）。GC 标记时只检查簇根是否可达——整个簇作为一个单元，不需要逐个遍历簇内对象。对资源密集的项目能显著减少 GC 标记时间。代价：簇内对象不能单独释放。
**考察**：性能优化深度

## 7. UE 反射 → UHT → Blueprint 调用链路

### Level 1: 基础认知
**面试官**：UE 的反射系统是怎么实现的？
**答**：编译前 UHT（Unreal Header Tool）解析 UCLASS/UPROPERTY/UFUNCTION 宏，生成 `.generated.h` 和 `.gen.cpp`，在引擎启动时注册类型信息到 UClass。运行时可以通过 UClass 遍历属性、查找函数、动态创建对象。
**考察**：反射基本机制

### Level 2: Blueprint 调用 C++ 的完整链路
**追问**：Blueprint 里调用一个 C++ 的 UFUNCTION，底层经历了什么？
**答**：Blueprint 编译为字节码 → 执行到函数调用节点 → 通过函数名查找 UFunction → UFunction 检查是否 Native（C++ 实现）→ 如果是 Native，调用 UFunction::Invoke() → 通过 ProcessEvent() 把参数打包为字节数组 → 调用 C++ 函数 → 返回值写回字节数组 → Blueprint VM 继续执行。
**考察**：调用链路深度

### Level 3: 性能影响
**追问**：反射调用比直接 C++ 调用慢多少？怎么优化？
**答**：Blueprint→C++ 调用开销约是直接 C++ 调用的 5-10 倍（ProcessEvent 打包参数 + 函数查找）。优化：(1) 热路径用 C++ 实现，只在逻辑层用 Blueprint；(2) 用 BlueprintNativeEvent 让 C++ 有默认实现；(3) Nativize Blueprint（编译为 C++，UE4 支持，UE5 部分支持）。
**考察**：性能优化能力

## 8. 帧同步 → 确定性 → 预测回滚

### Level 1: 基础认知
**面试官**：帧同步是什么？和状态同步有什么区别？
**答**：帧同步只同步输入——所有客户端收到相同的输入序列，各自独立计算得到相同结果。状态同步由服务器计算权威状态，客户端只显示。帧同步带宽极低（只传输入），但要求确定性；状态同步带宽高但不要求确定性。
**考察**：网络同步基本概念

### Level 2: 确定性
**追问**：怎么保证确定性？浮点数确定性吗？
**答**：(1) 固定帧步长（所有客户端相同 dt）；(2) 确定性随机数（共享种子）；(3) 浮点数**不保证确定性**——不同平台/编译器/优化级别的浮点运算结果可能不同（IEEE 754 对中间精度没有严格规定）。解决方案：定点数（`int32` 模拟小数），或保证所有客户端相同平台+相同编译选项。
**考察**：确定性理解深度

### Level 3: 预测回滚
**追问**：Rollback Netcode 的工作原理？
**答**：客户端不等待服务器确认，先用预测输入执行（本地操作零延迟）。收到服务器确认帧后，如果和预测不同：回滚到确认帧状态 → 用服务器输入重新模拟 → 快进到当前帧。需要：(1) 状态可快照/恢复；(2) 确定性模拟；(3) 快进能力（一帧内模拟多帧）。GGPO 是经典实现。
**考察**：网络架构设计

### Level 4: 防作弊
**追问**：帧同步怎么防作弊？
**答**：帧同步的防作弊比状态同步难——客户端有全部游戏状态（透视挂无解）。可做的：(1) 输入合法性校验（服务器/其他客户端验证输入是否合理）；(2) 结果校验——所有客户端每隔 N 帧上报状态哈希，不一致则判定作弊；(3) 延迟输入（不让客户端看到未来帧的对手输入）。本质上帧同步不适合强对抗 PVP，适合 MOBA/RTS/格斗这类可接受一定作弊风险的品类。
**考察**：架构取舍能力

## 9. ECS → 数据局部性 → Archetype vs Sparse Set

### Level 1: 基础认知
**面试官**：ECS 是什么？和传统 OOP 有什么区别？
**答**：Entity-Component-System。Entity 只是 ID；Component 只是数据（无逻辑）；System 只有逻辑（操作 Component）。和 OOP 的区别：OOP 是"对象 = 数据 + 行为"，ECS 是"数据和行为分离"。好处：数据连续内存排列 → Cache 友好 → 批量处理性能极高。
**考察**：架构模式理解

### Level 2: 数据局部性
**追问**：为什么 ECS 性能好？Cache 友好具体是什么意思？
**答**：ECS 把同类型 Component 连续存储在数组中。System 遍历时是线性访问连续内存——CPU Cache Line 预取命中率极高。传统 OOP 的 GameObject 散布在堆内存各处，遍历时指针追踪导致 Cache Miss 频繁。实测：ECS 遍历 10 万个 Entity 的 Position 组件可以比 OOP 快 10-50 倍。
**考察**：底层性能理解

### Level 3: Archetype vs Sparse Set
**追问**：Archetype 存储和 Sparse Set 存储有什么区别？
**答**：**Archetype**（Unity DOTS、UE Mass Entity）：按组件组合分组——所有有 {Position, Velocity} 的 Entity 放在一个 Archetype 的连续数组中。优点：遍历极快（一个 Archetype 内存完全连续）。缺点：添加/删除组件要搬移到另一个 Archetype。**Sparse Set**（EnTT、Flecs）：每种 Component 独立一个密集数组 + 一个稀疏映射表。优点：添加/删除组件 O(1)。缺点：多组件联合查询时跨数组访问，Cache 不如 Archetype。
**考察**：数据结构设计能力

## 10. 对象池 → 内存池 → Slab 分配器

### Level 1: 基础认知
**面试官**：对象池是什么？为什么游戏中常用？
**答**：预先分配一批对象放在池中，需要时取、用完归还，避免运行时频繁 new/delete。游戏中常用于子弹、特效、NPC——这些对象频繁创建销毁，new/delete 的开销和内存碎片会导致卡顿。
**考察**：基本概念

### Level 2: 内存池
**追问**：内存池和对象池有什么区别？
**答**：对象池管理"已构造的对象"——取出即可使用。内存池管理"原始内存块"——分配出去的是裸内存，需要 placement new 构造。内存池更底层、更通用，对象池是内存池 + 类型特定初始化的封装。
**考察**：分层理解

### Level 3: UE 的内存分配器
**追问**：UE 的内存分配体系是怎样的？
**答**：UE 有三层：(1) `FMalloc` 抽象层——平台无关的分配接口；(2) 具体实现——`FMallocBinned2`（默认，Slab 分配器思路，按大小分桶管理）/ `FMallocAnsi`（直接用 CRT malloc）/ `FMallocTBB`（Intel TBB）；(3) 上层封装——`FMemory::Malloc/Free`。Binned2 按对象大小分桶（8B/16B/32B/...），同大小的分配从同一个桶的连续内存块中分配——减少碎片、提高 Cache 命中。
**考察**：引擎底层知识

## 11. 渲染管线 → Early-Z → GPU Driven

### Level 1: 基础认知
**面试官**：渲染管线的主要阶段是什么？
**答**：顶点阶段（顶点着色器 → 曲面细分 → 几何着色器）→ 光栅化 → 片元阶段（片元着色器 → 逐片元测试）→ 混合 → 帧缓冲。逐片元测试顺序：Scissor Test → Stencil Test → Depth Test → Blending。
**考察**：管线基本知识

### Level 2: Early-Z
**追问**：什么是 Early-Z？什么情况下 Early-Z 会失效？
**答**：Early-Z 是 GPU 的优化——在片元着色器之前做 Depth Test，不通过的片元直接丢弃，省去着色计算。失效情况：(1) 片元着色器中修改了深度值（`gl_FragDepth`）；(2) 使用了 discard/clip（Alpha Test）；(3) 开启了 Alpha Blending（需要先着色再混合）。所以不透明物体从前往后排序渲染效率最高（最大化 Early-Z 收益）。
**考察**：GPU 优化理解

### Level 3: GPU Driven Rendering
**追问**：什么是 GPU Driven Rendering？
**答**：传统渲染：CPU 遍历场景 → 剔除 → 生成 Draw Call → 提交 GPU。GPU Driven：把剔除和 Draw Call 生成也放到 GPU 上——用 Compute Shader 做视锥剔除/遮挡剔除 → Indirect Draw 直接在 GPU 端发起绘制。好处：减少 CPU-GPU 之间的数据传输和同步，Draw Call 数量不再受 CPU 瓶颈。UE5 的 Nanite 就是 GPU Driven 的典型实现——用 Compute Shader 做虚拟几何体的可见性判断和三角形级别的剔除。
**考察**：前沿技术理解

## 12. 资源异步加载 → 线程模型 → 主线程回调安全

### Level 1: 基础认知
**面试官**：为什么资源加载需要异步？
**答**：同步加载会阻塞主线程——加载一个大的 StaticMesh 可能需要 50ms+，导致明显卡顿。异步加载把 IO 和反序列化放到后台线程，主线程继续 Tick，加载完成后回调通知。
**考察**：基本动机

### Level 2: 线程模型
**追问**：异步加载的线程模型是怎样的？IO 线程和解析线程是同一个吗？
**答**：UE 的异步加载分两层：(1) IO 线程做磁盘读取（FFileReadAsyncHandle）；(2) AsyncLoadingThread 做反序列化和 UObject 创建。两者可以流水线——IO 线程读完一个包的数据后，AsyncLoadingThread 开始解析，同时 IO 线程读下一个包。最终的 PostLoad/回调回到 GameThread 执行。
**考察**：线程架构理解

### Level 3: 主线程回调安全
**追问**：为什么回调必须在主线程？如果我在后台线程创建 UObject 会怎样？
**答**：UObject 的注册（加入 GC 系统、设置 Outer、PostInitProperties）不是线程安全的——GC 可能在任意时刻运行，如果后台线程正在创建 UObject 而 GC 恰好开始标记，会导致对象状态不一致（crash 或内存损坏）。所以 UE 强制：UObject 的创建和重要生命周期回调必须在 GameThread。AsyncLoadingThread 只做数据反序列化到中间结构，最终的 UObject 构造交给 GameThread。
**考察**：线程安全深度理解

### Level 4: 优先级和取消
**追问**：如果你设计一个资源加载系统，怎么处理优先级和取消？
**答**：优先级：用优先级队列管理待加载请求，高优先级请求排在前面。但正在 IO 的请求不能被打断——只能在"下一个请求"时体现优先级。取消：取消标志位——IO 完成后检查是否已取消，如果取消则丢弃数据不进入反序列化阶段。注意：已经创建的 UObject 不能简单丢弃，需要 MarkAsGarbage 让 GC 回收。FStreamableHandle 的 CancelHandle 就是这个思路。
**考察**：系统设计能力
