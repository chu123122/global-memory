## 2. 技术风险 — 🔴 BLOCK

**发现**:

- 🔴 **DESIGN §3.3 / §3.4 / §3.5 三处声称的"复用"在现实代码中并不存在**,这是阻塞性问题:
  - §3.3 "复用已有的 `_atomic_append_jsonl()`" — `D:/global-memory/harness/panel_api.py` 当前**只有** `append_event()`(第 26-29 行),实现是 `f.write(json.dumps(...) + "\n")`,**无原子性保证、无文件锁、无 schema 校验**。`_atomic_append_jsonl` 这个函数名根本不存在。
  - §3.4 "复用 `harness/_lib.py` 的 `rotate_log()`(已存在,被 audit hook 用过)" — `_lib.py` 的导出函数仅 `now_str / today_str / git_last_modified / extract_yaml_field / scan_topic_files / count_all_memory_files / write_log` 7 个,**没有 `rotate_log`**。grep `rotate` 在整个 harness/ 下也找不到。
  - §3.5 "已有 `harness/_lib.py` 的 `is_windows()` 工具" — `_lib.py` 中**没有 `is_windows()`** 函数。
  - ADR-005 "Phase 4-A 实现需用文件锁(`portalocker` 或自旋 + `os.O_APPEND`)" 加上 DESIGN §3.5 "`portalocker`(已是 `harness/requirements.txt` 依赖,verify 一下确认)" — 实际项目无 `requirements.txt` 引用 portalocker,grep `portalocker` 在 harness/ 下也无匹配。

  影响:Phase 4-A 实际工作量从 §3.3 估的"~40 行 + 复用"暴涨到 ~200 行(自己写原子 append + 自己写 rotate_log + 自己写 is_windows + 引入 portalocker 依赖或写 fcntl fallback),且需要为这些新工具加单测。这会让 4A-V3 / 4A-V4 验收落地难度从"复用现成实现"变成"从零写并发安全代码 + 跨平台测试",**这是一个 C++ 短板用户(自陈"C++ 多线程是短板")需要做并发文件 IO**——风险叠加。
- 🟡 **§3.4 阈值与现实数据不匹配**。ADR-005 说"日均 ~50 条事件,5 MB 大约 3-4 个月一次轮转";但 Phase 4-A 写入对象是 `task_outcomes.jsonl`,频率是"每个 Phase 完成一次",日均最多 1-2 条(本任务 9 Phase 即使全做完也才 9 行,< 1KB)。5 MB 阈值对账本实际意味着"几年都不会触发轮转",轮转代码在 Phase 4-A 完全是死代码,验收 4A-V4 必须靠 mock 文件才能跑通——**可能根本不该在 Phase 4-A 写轮转,推迟到 Phase 4-B 或者降到"轮转留接口、不实现"**。
- 🟡 **§1.2 数据流图与 settings.json 实际配置有偏差**。settings.json 实际挂的是 7 个 hook 命令(audit_logger / dangerous_command_blocker / memory_file_protector / doc_gate / diff_backup / diff_show / subagent_logger),REQUIREMENTS §2 / DESIGN §1.2 / V7 都说"6 hooks";到底是 6 还是 7 影响 V7 的验收行数(12 vs 14 用例)。Phase 1-B 矩阵 v1(V5 要求行数 ≥ 12)若按 6 hooks 算只能勉强达标,按 7 算更宽裕。
- 🟡 **§1.2 数据流图把 post_task_hook 画在 L2 维护层,但 settings.json 它实际挂在 Stop hook 上,且执行 `--auto-fix` 自动 commit**——这正是 §10.1 的噪音根源。把它归 L2(维护)并放在 daemon 框里掩盖了它其实是个"硬阻断/硬副作用 hook",归 L3 更合适;不归对会让 §10.1 的解决方向(候选 A/B/C/D)无法在终态架构里找到归宿层。
- 🟡 **§3.7 Phase 0/4-A 并行执行序的实际可行性**。文档描述的"先 Phase 0 commit 1 → Phase 4-A 全做 → Phase 0 commit 2/3"这条路径有个隐藏假设:Phase 0 commit 2 批量 mv 时,Phase 4-A 已经写入的 task_outcomes.jsonl 第 1 条记录里 `task=harness-governance-v1, phase=0` **早于 Phase 0 完成**——也就是 4A-V5 的"自身写第 1 条"在 Phase 0 真正完成之前就被写入了,**记录的是"Phase 0 commit 1 完成"还是"Phase 0 全完成"语义不清**。schema 没有 `partial_completion_at_record_time` 字段。
- 🟡 **G1/G2/G3 治理元规则的执行机制缺失**。规则 G2 说"没有引用区 = 在搞独立王国",但**没有任何脚本/hook 强制检查这件事**——靠 AI 自觉,等于 §1.3 信任边界 S3 级别。但 G1/G2/G3 自身在文档里被描述成"必须",存在**强制级别与执行机制的强度不匹配**。
- 🟡 **ADR-006 / ADR-007 / ADR-004 在 §1.4 表格、Phase 0 §2 引用区、Phase 4-A §3 引用区均被显式引用,但 decisions/README.md 索引和实际文件均不存在**(README 里只列了 4 个 ADR,且明确写"按需补充")。这是用户特别关注的"悬空 ADR 引用"——三处 Phase 设计文档已经依赖这些 ADR 的具体决策(变更兼容期策略、schema_version 兜底、中英文命名理由),但决策本身只是被命名,内容未写。如果这些 ADR 推迟,那 Phase 0 / Phase 4-A 在写实施 commit 时可能发现 ADR 决策与已写代码冲突,导致返工。

**建议**:

- **(P0)** 在动手实现 Phase 4-A 之前,**修订 §3.3 / §3.4 / §3.5 / ADR-005**,把"复用 X" 改成 "新建 X(单测在 Phase 4-A 范围内)"。或者提前(本周内)把 `_atomic_append_jsonl` / `rotate_log` / `is_windows` 三个工具加进 `_lib.py` 并加单测,作为 Phase 4-A 的前置子任务(可命名 Phase 4-A.0 工具铺设)。
- **(P0)** 把"是否 vendoring portalocker / 用 stdlib fcntl+msvcrt 写 fallback / 不解决 Windows 并发(单 writer)"作为一个显式 Phase 4-A 子决策,落 ADR-008 或写进 §3.5。当前一句"如果不在依赖里,写一个 50 行的 fcntl-fallback"含混了 Windows 平台不存在 fcntl 这个事实——`fcntl` 是 POSIX-only 模块,Windows 必须用 `msvcrt.locking()` 或 portalocker,**fcntl-fallback 在 Windows 上根本 import 不进来**。
- **(P1)** Phase 4-A 砍掉轮转实现,只在 schema 里留 `schema_version` + 写入端只 append。轮转推到 Phase 4-B 与 reader 一起实现(reader 本来就要支持多文件聚合)。这样 4A-V4 验收转移到 Phase 4-B,Phase 4-A 只剩 4A-V1/V2/V3/V5 四条,减少 1 个 mock-only 验收。
- **(P1)** 统一 hooks 计数:决定按"hook 文件数 = 7"还是"hook 类别数 = 6"(把 diff_backup + diff_show 视为一对),REQUIREMENTS V7 / DESIGN §1.2 / V5 的行数门槛同步对齐。建议按"hook 文件数"算更实(脚本数量是物理事实)。
- **(P1)** 把 post_task_hook 在 §1.2 数据流图里挪到 L3 阻断层 + L2 维护层中间(它确实横跨二者:写 git = L3 副作用,清理 = L2 维护)。或者干脆给它单独立"L2.5 自动副作用层"——这样 §10.1 解决方案 A/B/C/D 有归宿。
- **(P2)** §3.7 4A-V5 改成"Phase 0 commit 3 完成且 grep 验证清零之后再写 outcome,phase 字段用 `0` 表示完整 Phase 0,不在 commit 1/2 阶段写中间状态"。或者增加 `outcome` 枚举值 `partial-commit`。
- **(P2)** ADR-004 / ADR-006 / ADR-007 三个被引用的 ADR 设定**截止时间**(如:Phase 0 commit 1 之前必须写完 ADR-004 + ADR-006;Phase 4-A 实现之前必须写完 ADR-007),不允许 Phase 设计文档先于决策文档定型。或者退一步,把它们标 `Proposed` 状态先占位,正文写"详见 §1.4 第 N 条"指回 DESIGN,起码不悬空。

## 3. 替代方案评估 — 🟡 CONDITIONAL

**发现**:

- 4 个已写 ADR 的"候选方案 A/B/C → 选 A 理由"结构很完整,trade-off 写得清楚——这维度的方法论是合格的。ADR-001 的 A/B/C 三方案 + 选定理由 + 风险互引 ADR-005/ADR-007,是模板级别。
- **但 ADR 与 DESIGN 之间存在 trade-off 重复**。例如 ADR-005 已经讨论了 append-only vs 就地改 vs 不轮转;DESIGN §3.4 又重复讲了一遍轮转策略;DESIGN §3.5 重复讲了一遍并发与原子性。**ADR 应是决策的最终归宿,DESIGN 的 §3.4/3.5 应该退化成"参见 ADR-005"+ 实现细节(具体阈值、调用代码)**。当前 DESIGN 重复了 ADR 的论证过程,后续修订 ADR 时容易出现"改了 ADR 没改 DESIGN"的漂移——刚好是 Phase 2-B 漂移扫描要解决的问题在自己身上发生了。
- **§1.4 横切原则表的"对应 ADR" 列与实际 ADR 内容存在轻微错位**。原则 4 (中文 vs 英文) 标 ADR-004,但 ADR-004 未写;原则 6 (变更兼容期 + 拆 commit) 标 ADR-006,但 ADR-006 未写。这就是用户特别关注的悬空引用——4 个原则中有 3 个(4/6/7)指向不存在的 ADR。如果未来"中文 vs 英文"的决策推翻(比如发现中文文件名在 git log 里乱码),没有 ADR 文件可以 supersede,只能改 §1.4 表格——违反 G3"ADR 不可删,只可 supersede"。
- **Phase 0 三 commit 拆分的替代方案没讨论**。§2.4 直接给出"3 commit"拆分,没说"为什么不是 1 个原子 commit / 也不是 5 个细 commit"。3 个 commit 的灰度兼容期是 Commit 2 之前 = 短(几分钟到几小时),实际收益(可回滚 commit 1 不影响存量、可回滚 commit 2 不破坏 commit 1 的脚本支持)是真实的,但 trade-off 没显式写——读者(包括 6 个月后的自己)不知道"为什么不能合并 commit 1+2"。
- **§3.2 schema v1 的字段克制讨论很好**(显式说明不加 `failure_reason_classification` / `task_type` / `tags`),但**没有讨论 `phase` 字段为可选的 trade-off**。如果同任务多 Phase 都不写 phase,reader 怎么区分?(可能靠 ts 排序近似,但不显式)。
- **§3.7 Phase 0/4-A 并行的"更干净方案"没讨论**。用户特别关注问。可以考虑的备选方案:
  - 方案 X:Phase 4-A 不依赖 Phase 0(写入路径用 stable 的 logs/ 路径,与文档命名解耦),4A-V5 推到 Phase 0 完成后单独跑——已经是当前事实方案,但未显式

  - 方案 Z:把 4A-V5 从 Phase 4-A 验收里拿出来,放到任务级最终验收。Phase 4-A 验收只到 V1-V4

## 4. 可测试性/可维护性 — 🟡 CONDITIONAL

**发现**:

- **Phase 0 §2.5 P0-V1 ~ V5 验收方法都是手动跑命令 + grep + 单测**,可测试性合格。test_stage_lib.py 增双名用例是好做法。

- **G3 ADR 不可删** 同样无强制。grep `Superseded by` 计数对账可以加进 Phase 2-B 的漂移规则,但目前没有。
