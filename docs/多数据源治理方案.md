# 多数据源治理方案

> 全系统多数据源(文本/代码/配置散落会漂)统一治理框架。hook 链是首个实例(M1)。
> 源: `multisource-audit` workflow 盘点 26 cluster。
> **状态（2026-06-04）**：`reconcile.py` MVP 已实现（M1 manifest→doc 渲染 + 扫标记动态构建 + --check/--fix，首个 cluster = 主循环 hook 表，TDD 全绿）。剩余：M2/M3/M4 模式、settings/bootstrap 渲染（触 hook 安装链，须确认）、meta-check 启发式。

## 问题

同一份数据散在 **文本(doc) / 代码(.py 硬编码) / 配置(.json/yaml)** 多处，手维护必漂。全系统盘点出 **~26 个多源 cluster**。现有 `check_*/scan_*` 多为**只检测不修**，改一处要手追多处，漏一处巡检报红。hook 链只是其中漂险最高的一个。

## 0. 全局机制（地基）—— 发现，不枚举

**判据**：全局 ≠「我列得够全」，而是「**没列到的、未来才加的多源点，能否自动被纳入**」。手写 cluster 清单本身就是个会漂会缺的数据源——框架犯了它要治的病。所以靠**发现**：

### 自声明 + 全仓扫描

```
每个派生面在自己身上声明归属:
  doc 表:   <!-- RECONCILE: source=hook_manifest.json pattern=M1 -->...<!-- /RECONCILE -->
  配置镜像: 头部 frontmatter 标 reconcile.source / reconcile.pattern
        │
reconcile.py 扫全仓所有 RECONCILE 声明 → 运行时构建 cluster 集
不读手写清单。cluster 集 = 扫出来的。
```

- 加 cluster #27 = 在那个派生面**丢一个标记**，下次跑自动治理，**reconcile.py 一行不改**。
- 稳定有界的只有 **4 个模式类（M1-M4）**。模式不繁殖；繁殖的实例靠扫。
- **框架治自己**：无手写 cluster-list（本文 §1 全景表 = 人读快照，**非脚本输入**，脚本只认标记）。

### 完整性兜底（治"漏标记"）

元检查（启发式）：扫到「md 表格列 ≈ 某 json 字段」「README 数字 = 某文件计数」等**疑似镜像但无标记** → 报「疑似未治理多源」→ 人裁定（补标记 or 确认无关）。把框架自己的覆盖盲区也变可巡检。

### 残留
- 全新多源**形态**（4 模式套不上）→ 仍要人设计 M5 子类。模式是设计的不是扫的，有界罕见。
- 元检查有误报/漏报——是"提醒人看"，非判定。

## 2. 四通法模式

| 模式 | 机制 | 唯一源 | --fix 能力 |
|------|------|--------|-----------|
| **M1 单源+渲染+check** | 结构化源 → 渲染 doc/settings/计数；`--check` 比对漂移 | manifest(json/yaml) | **全自动** |
| **M2 磁盘=实况+清单+孤儿扫描** | 文件系统是真源，清单声明应有；双向 diff（orphan/dead-ref） | 磁盘 | **半自动**（补声明可，删实体禁→needs-human） |
| **M3 单源 section+引用** | 权威文本写一处，余者链接不手抄；只能验引用指针存在 | 某 doc 的某 section | **仅 check**（语义机器判不了） |
| **M4 词表+覆盖率校验** | 受控词表是源，消费方取值于词表，校验覆盖率 | vocab.yaml | check(+阈值) |

## 3. 每 cluster 套哪种

- **M1**：Hook 链、Capability、Maintenance 表、README 边界、settings 渲染、registry **计数**部分
- **M2**：Script orphan、Task 存储、Publish scope、MEMORY 索引、task_display_names dead-ref、Skill 硬编码（改动态扫描）
- **M3**：Prompt/Agent 安全边界、规则文本重复、Lane 路由、审查 Agent 约束、subsystem-map **描述**部分
- **M4**：triggers_vocab、client claim_policy

## 4. 统一脚本：`reconcile.py` 插件式

**一个脚本 + 4 个有界模式类**（注册的是**模式**不是**实例**；实例靠 §0 扫标记动态构建——这才不会再造一组会漂的 check_*）：

```
reconcile.py --check|--fix [--only <cluster>] [--strict] [--json]
  1. 扫全仓 RECONCILE 标记 → cluster 集 (动态, 非硬编码)
  2. 每 cluster 按其声明的 pattern 派发给对应模式类
  registry: pattern_id -> PatternClass   (只 4 条, 有界稳定)
  接口: load_source() / load_derived() / diff() / render()
  M1 ManifestRender  : render → --fix 全自动
  M2 DiskClaimScan   : --fix 仅补声明; 删实体 → needs-human (恢复边界:不可逆)
  M3 ReferenceCheck  : 仅 --check 引用指针; 语义靠人 review
  M4 VocabCoverage   : --check 覆盖率阈值
  + meta-check: 疑似未标记镜像 → 报 needs-human (§0 兜底)
```

统一退出码 + JSON 报告，接入现有 `quality_gate` / `release-check` / gate。`--fix` 仅 M1/M4 全自动；M2 半自动；M3 只读。**保留「检测/修复」分层**，与 harness 现状平滑过渡。

## 5. 优先级（漂险 × 改动频率）

1. **Hook 链（M1）** — high×高频，首治打样，收益最大
2. **Prompt/Agent + 规则重复（M3）** — high×中频，5 处手抄安全边界易语义漂；先做引用指针校验（低成本），语义留残留
3. **Maintenance 表 + Capability（M1）** — 纯渲染 ROI 高
4. **Task 存储 / display_names（M2）** — 已知 14 dead-ref，清理 + 月检
5. **triggers_vocab（M4）** — 已有 G4，补 reconcile 收口
6. 低优：Publish scope、Script orphan、Hook 枚举

## 6. 残留 + 尊重既有决策

机器堵不死，**必须人工 / 不可自动**：
- **M3 语义等价**：「审查只读不改」5 处措辞各异，机器只验引用存在，改写是否仍等价靠人 review。
- **M2 删除侧**：orphan/dead-ref 检得出，删文件/删 task 不可逆 → 只标记。
- **subsystem-map 叙述 / Lane「就地判断」语境**：「为什么这样设计」无源可派生，半手写。

**调和既有决策**（召回 `harness-doc-completion`）：
> 「注册表手维护带语义，不自动生成」「孤儿巡检只报告不自动删」

不冲突——本方案只渲染**机械部分**（计数/路径/接线/枚举），**语义描述**（为什么、用途叙述）仍人手。M2 删除=needs-human 正对齐「不自动删」。即：**自动化机械同步，保留语义人控。**

## 7. 待验（证据不足）

- bootstrap.py REPORT 枚举是否真无消费方 → 删前 grep 全仓确认。
- Task 存储三源（env / projects / ClaudeTasks）权威关系 → 建议唯一源 projects/ 的可行性未验。

## 8. 落地顺序

```
1. 写 reconcile.py 骨架 + Reconciler 接口 + 注册表
2. 首装 M1·Hook 链(打样): doc 表插 marker 块 → reconcile --fix 首渲染 (已完成 §9)
   注: bootstrap 已读 manifest, 无第二源可杀(§10 更正)
3. --check 进 gate 守门
4. 测试: 改 manifest 一处 → --fix → settings+3doc 同步; 手改块 → --check FAIL
5. 验证后复制模式装 M1 其余(Capability/Maintenance) + M3 引用校验 + M4
6. M2 task 存储清 14 dead-ref(needs-human 确认删)
```

## 9. 实现进度 + 首次运行发现（2026-06-04）

**已实现**（`harness/scripts/reconcile.py` MVP）：
- 扫全仓 `RECONCILE` 标记动态构建 cluster（非硬编码清单，§0 地基）
- M1 `hook_table` renderer：`hook_manifest.json` → 逐 hook 表（event/matcher/hook/failure_action/性质，性质由 failure_action+event 推导）
- `--check`（漂移退 2）/ `--fix`（重写块）/ `--json`
- 首个治理 cluster：`docs/主循环与日志地图.md` 的逐 hook 表。TDD：占位→Red(drift,exit2)→--fix→Green(exit0)
- 已登记 capability_manifest(runtime_hook_governance) + scripts-registry，零新增巡检错误

**首次运行抓到真 drift**（验证框架有效）：
- `hook_manifest.json` **缺 `learning_opportunity_nudge`**（PostToolUse Bash），但 settings.json 有它 → manifest（声称源）与运行时不同步。这正是 bootstrap-第二源问题的实证。
- `learning_opportunity_nudge.py` 还同时是 capability unassigned + scripts-registry unregistered → 一个完全未纳管的 hook。修它属 manifest/settings 半（触安装链，须确认），记 backlog。

**已扩展（2026-06-04 第二轮）**：
- **M3 引用校验**：校验 `rules/*.md` 跨层引用指针（`../`/同目录 .md）目标存在。**首跑抓到 5 个真断链**（层规格误写 `../CLAUDE.md`，实际在 `../agents/CLAUDE.md`；`MEMORY.md` 应 `../MEMORY.md`）→ 已修。
- **M2 委托**：reconcile 调 `scan_orphan_scripts.py`（不重写，避免造新孤儿检查器），surface unregistered/stale。
- **meta-check**：启发式报「含多处 hooks/scripts 路径但无 RECONCILE 标记」的疑似镜像（advisory，不影响退出码）。首跑标出 5 个候选：capabilities / capability-map-and-oss-gap / gate-template / meta-evidence-pipeline / subsystem-map → 人工裁定是否补 M1 renderer 纳入。

**剩余**：M4（词表覆盖）= 既有 `gate_check.py` G4 已做，按需委托不重写；为 meta-check 标出的 5 候选写 M1 renderer；M1 推广到 capability/maintenance cluster。

## 10. 更正 + 纳管修复（2026-06-04）

**更正假设**：原 §1/§8 称「bootstrap.py 硬编码 hook 第二源」——**错**。实测 `bootstrap.hooks_json()` 已 `load_hook_manifest()` 从 manifest 渲染（statusLine 同样在 manifest）。bootstrap 不是独立源，是渲染器。「杀第二源」是不存在的活（multisource-audit workflow 未读码推断的假阳性，同「文件缺失」类）。真正能漂的是 **settings.json 被手改偏离 manifest**。

**修真 drift（纳管 learning_opportunity_nudge）**：`check_hook_alignment` verdict=drift，唯一 finding `runtime_not_in_bootstrap`：settings 有 `learning_opportunity_nudge` 但 manifest 没有。修：补进 hook_manifest(PostToolUse/Bash) + capability(runtime_hook_governance) + scripts-registry → reconcile --fix 重渲染 doc 表。结果：alignment drift→aligned；check_capability ERROR 3→2；scan_orphan unregistered 3→2。不需重装 settings（settings 已有，补源对齐即可）。
