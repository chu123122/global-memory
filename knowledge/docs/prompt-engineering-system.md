## Part 1: 场景 Prompt 模板库

---

### 模板 1: 代码审查

**角色设定**：你是一位有 10 年 UE 引擎开发经验的 Tech Lead。

**输入格式**：
```
## 审查请求
- 语言: [C++ / Lua / C#]
- 模块: [所属模块名]
- 变更描述: [1-2 句话说明这次改了什么]
- 重点关注: [性能 / 线程安全 / 内存 / 逻辑正确性 / 全部]

## 代码
[粘贴代码]
```

**输出格式要求**：
```
按严重程度分三级输出：
🔴 Critical（必须修）: 会导致 crash、数据损坏、安全漏洞
🟡 Warning（建议修）: 性能问题、不规范用法、潜在风险
🟢 Info（可选）: 代码风格、可读性改进

每条意见格式：
[严重程度] 行号 | 问题描述
  原因: 为什么这是个问题
  修复: 具体改法（给代码）
```

**使用示例**：
```
## 审查请求
- 语言: C++
- 模块: ResourceManager
- 变更描述: 新增异步资源加载接口
- 重点关注: 线程安全

## 代码
void UResourceManager::LoadAsync(const FSoftObjectPath& Path, FOnLoadComplete Callback)
{
    AsyncTask(ENamedThreads::AnyBackgroundThreadNormalTask, [this, Path, Callback]()
    {
        UObject* Loaded = StaticLoadObject(UObject::StaticClass(), nullptr, *Path.ToString());
        CachedResources.Add(Path, Loaded);
        Callback.ExecuteIfBound(Loaded);
    });
}
```

### 模板 2: 架构设计

**角色设定**：你是资深游戏引擎架构师，擅长在性能、可维护性、开发效率间取舍。

**输入格式**：
```
## 需求
[用 1-3 句话描述要做什么]

## 约束
- 引擎: [UE5 / Unity / 自研]
- 性能要求: [帧耗时预算 / 内存预算]
- 已有系统: [需要对接的现有模块]
- 团队规模: [几人维护]

## 特别关注
[可选：线程安全 / 热更新 / 可扩展性 等]
```

**输出格式要求**：
```
输出 2-3 个设计方案，每个方案包含：
1. 方案名称 + 一句话概述
2. 模块划分（类图/模块图文字版）
3. 核心数据结构
4. 关键接口定义（C++ 伪代码）
5. 数据流描述

最后输出对比表：
| 维度 | 方案A | 方案B | 方案C |
|------|-------|-------|-------|
| 性能 | ... | ... | ... |
| 复杂度 | ... | ... | ... |
| 可扩展性 | ... | ... | ... |
| 推荐指数 | ⭐⭐⭐ | ⭐⭐ | ⭐ |

最后给出推荐方案和理由。
```

**使用示例**：
```
## 需求
为 UE5 项目设计一个独立的多线程资源加载插件，支持优先级调度和取消。

## 约束
- 引擎: UE5.3
- 性能要求: 加载不阻塞主线程，主线程 Tick 开销 < 0.5ms
- 已有系统: FStreamableManager（需兼容）
- 团队规模: 2人

## 特别关注
线程安全、优先级反转、取消操作的安全性
```

### 模板 4: Bug 排查

**角色设定**：你是 Debug 专家，擅长从现象推理根因。

**输入格式**：
```
## Bug 描述
- 现象: [具体表现，越详细越好]
- 频率: [必现 / 概率 / 特定条件]
- 环境: [平台、引擎版本、Debug/Release]
- 复现步骤: [1. 2. 3.]
- 已排查: [已经试过什么，排除了什么]

## 相关信息
[日志 / Callstack / 截图 / 代码片段]
```

**输出格式要求**：
```
1. 初步分析（基于现象推断的可能原因，按可能性排序）
   - 可能性 1 (70%): ...
   - 可能性 2 (20%): ...
   - 可能性 3 (10%): ...

2. 排查方案（针对每个可能性）
   - 怎么验证
   - 需要看哪些代码/日志
   - 加什么断点/日志

3. 修复建议（如果能确认根因）
```

**使用示例**：
```
## Bug 描述
- 现象: PIE 模式下频繁出现 "Accessed None" 崩溃
- 频率: 约 30% 概率，切换关卡时
- 环境: UE5.3, Win64, Development Editor
- 复现步骤: 1.打开编辑器 2.Play 3.切换关卡 4.约30%崩溃
- 已排查: 检查了 Actor 的 BeginPlay，没有空指针

## Callstack
[粘贴 callstack]
```

## Part 2: AI 辅助开发工作流 SOP

---

### 阶段 1: 需求分析

**流程**：
```
模糊需求 → 结构化 Prompt → AI 输出分析 → 人工确认

Prompt 模板：
"我收到以下需求：[原始需求文本]

请帮我：
1. 提取核心功能点（列表形式）
2. 识别模糊/缺失的信息（需要和 PM/主程确认的问题）
3. 技术选型建议（列出候选方案及 trade-off）
4. 拆解为可执行的子任务（每个有明确输入/输出）
5. 预估每个子任务的工作量（人天）"
```

**UE C++ 示例**：
```
需求：给元梦之星的装扮系统增加"试穿预览"功能，
玩家在商城可以预览装扮效果，不阻塞商城 UI。

AI 输出应包含：
- 核心功能：异步加载装扮资源 → 临时 Actor 生成 → 预览相机 → 退出清理
- 缺失信息：预览是否需要动画？是否支持多件同时预览？
- 技术选型：FStreamableManager 异步加载 vs UAssetManager
- 子任务拆解：1.预览数据接口 2.异步加载管理 3.预览场景搭建 4.UI 集成
```

---

### 阶段 2: 设计

**流程**：
```
子任务 → 架构设计 Prompt（模板2）→ AI 输出多方案 → 选择方案 → 详细设计

详细设计 Prompt：
"基于我们选定的方案 [X]，请输出详细设计：
1. 完整类图（文字描述版，列出所有类及其关系）
2. 核心数据结构定义（C++ struct/class）
3. 关键函数签名及注释
4. 数据流（从输入到输出的完整链路）
5. 线程模型（哪些操作在哪个线程）
6. 错误处理策略
7. 性能关键路径分析"
```

---

### 阶段 3: 编码

**分块生成策略**：
```
大型系统不要一次性让 AI 生成全部代码。按以下顺序分块：

第 1 轮：核心数据结构 + 接口声明（.h 文件）
  "请根据上面的设计，先生成头文件，只包含：
   类声明、公共接口、关键成员变量。不要实现。"

第 2 轮：核心逻辑实现（.cpp 的关键函数）
  "现在实现以下函数：[函数名列表]
   每个函数需要：实现代码 + 行内注释解释关键决策"

第 3 轮：边界处理和错误处理
  "为以下接口添加完整的错误处理：
   - 参数校验
   - 异常情况处理
   - 日志输出"

第 4 轮：单元测试
  "为以下类生成单元测试：
   - 正常路径测试
   - 边界条件测试
   - 多线程并发测试（如适用）
   使用 UE 的 Automation Test 框架"
```

---

### 阶段 4: Review

**AI Code Review Prompt**：
```
"请审查以下代码，你是一位 UE 引擎的 Tech Lead。

审查维度（按优先级）：
1. 🔴 线程安全：是否有数据竞争、死锁风险、主线程阻塞
2. 🔴 内存安全：是否有泄漏、悬垂指针、double free、UPROPERTY 遗漏
3. 🟡 性能：不必要的拷贝、Cache 不友好、算法复杂度
4. 🟡 UE 规范：命名、UPROPERTY/UFUNCTION 标记、GC 安全
5. 🟢 可维护性：耦合度、函数长度、注释质量

[粘贴代码]

输出格式：按严重程度分类，每条给出行号、问题、原因、修复代码。"
```

## Part 3: Prompt 编写最佳实践清单

| 原则 | 说明 |
|------|------|
| **角色先行** | 开头定义 AI 角色（"你是 UE Tech Lead"），输出质量显著提升 |
| **结构化输入** | 用 Markdown 区块组织输入，而非一大段自然语言 |
| **明确输出格式** | 告诉 AI 用什么格式输出（表格/列表/代码块），否则输出不可预测 |
| **给示例** | 输入示例 + 期望输出示例 > 大段描述 |
| **分步执行** | 复杂任务拆成多轮对话，每轮聚焦一个子任务 |
| **约束优于自由** | "不要做 X" 比 "尽量做 Y" 更有效 |
| **提供上下文** | 告诉 AI 你已有的知识、项目背景、引擎版本 |
| **迭代优化** | 第一次输出不满意 → 指出具体问题 → 让 AI 修改，而非重新描述需求 |
