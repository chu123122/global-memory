# Requirements · runtime-compatibility

> 文档类型：**需求分析（Requirements Analysis）**
> 创建：2026-04-24
> 任务目录：`projects/runtime-compatibility`
> Status: discussion
>
> 本文档回答：为什么要让 global-memory harness 在非 Claude Code 环境下也能工作，以及本期到底做到什么程度。

---

## 1. 当前痛点

global-memory 现在能跑起来，但一等运行时明显是 Claude Code：`~/.claude/settings.json`、hooks、agents、skills、Stop hook 自动同步都围绕 Claude Code 设计。换到 Codex、Cursor、Continue、OpenAI API 或普通终端后，体系不会完全失效，但会从“自动接管工作流”退化成“人手动读文档、手动跑脚本”。

这会带来两个具体问题：

- **AI 不知道入口**：非 Claude Code 不一定会自动读 `agents/CLAUDE.md`、`skills/work/SKILL.md`，也不知道先跑 `maintain.py status/doctor`。
- **安全边界变软**：Claude Code hook 能硬拦危险命令、写文件前检查任务文档、Stop 后自动同步；其他环境通常只能靠 prompt 自觉。
- **面板状态断开**：GUI 已有本地事件入口，但外部 AI 没有统一约定，不一定知道怎么把诊断结果写回面板。
- **维护认知分裂**：同一套 harness 在 Claude Code 下是“体系”，在别处像“一堆脚本”，新人或未来 AI 容易从错误入口开始。

## 2. 目标

本期目标不是让所有 AI 工具获得完全一样的能力，而是把运行时分层说清楚，并给非 Claude Code 一个最低可用路径。

```
Claude Code       → 完整自动化：hooks / skills / agents / auto-sync
Codex / CLI       → 可读规则 + 统一 CLI + 上下文导出 + 手动同步
Cursor / API      → 上下文包 + 操作边界 + 推荐命令
无 AI 环境         → GUI / maintain.py / check_health.py 可维护
```

要交付的是“兼容运行时底座”，不是重写 Claude Code 集成。

## 3. 方案选定

候选方案对比：

| 方案 | 描述 | 优点 | 缺点 | 风险 |
|---|---|---|---|---|
| A · 保持 Claude Code 专属 | 继续只优化 `.claude` hooks/skills | 成本最低，能力最强 | 离开 Claude Code 后体验断崖式下降 | 未来工具迁移成本越来越高 |
| B · 抽通用 Core + Runtime Adapter | 保留 Claude Code 深集成，另做通用导出和运行时能力矩阵 | 不牺牲现有体验，非 Claude Code 有最低路径 | 多一层 adapter 文档和测试 | adapter 漂移，需要维护 |
| C · 全面改成工具无关框架 | hooks/skills 全部抽象成通用协议 | 理论最通用 | 成本高，当前稳定功能容易被稀释 | 过度设计，短期不可控 |
| **选定 · B** | Claude Code 继续是一等运行时，其他环境作为兼容运行时 | 风险最低，收益直接 | 需要定义清楚降级边界 | 可通过 manifest 和测试收敛 |

本期选 B。原因很简单：Claude Code 专属能力是真有用，不该为了“通用”把硬拦截和自动同步弱化；但 `maintain.py`、GUI、文档和 Git 同步本来就能通用，应该把它们包装成清楚的 fallback。

## 4. 子决策记录

### 决策 1 · 不追求完全等效

非 Claude Code 环境没有统一的 tool lifecycle hook，本期不承诺 PreToolUse/Stop hook 等效。承诺的是：

- 能读懂当前体系。
- 能生成任务上下文。
- 能跑只读检查。
- 能把事件写到面板。
- 能通过统一 CLI 做安全修复和同步。

### 决策 2 · Claude Code 专属能力显式标注

文档和 manifest 中要区分：

| 能力 | 类型 |
|---|---|
| `maintain.py doctor/status/report` | 通用 |
| `control_panel.py` | 通用，本机 GUI |
| `panel_api.py notify` | 通用，本地文件事件 |
| `bootstrap.py install` | Claude Code 专属 |
| `settings.json hooks` | Claude Code 专属 |
| `skills/*/SKILL.md` 自动触发 | Claude/Codex 风格相关，不保证通用 |

### 决策 3 · 先做上下文导出，不先做 HTTP 服务

外部 AI 最需要的是一个可复制、可喂给模型的上下文包。HTTP/WebSocket 服务会引入端口、鉴权、生命周期管理，本期不碰。

## 5. 范围与验收

### 5.1 在范围内

| 类 | 项 |
|---|---|
| 文档 | 增加“运行时兼容层”说明，讲清 Claude Code 一等运行时和 fallback 路径。 |
| 设计 | 定义 Runtime Adapter、Context Export、能力矩阵和测试边界。 |
| CLI 后续实现 | 预留 `export-context` 或独立 `export_context.py`，给外部 AI 生成上下文包。 |
| GUI 后续接入 | 面板可展示外部 AI 通过 `panel_api.py` 写入的事件。 |
| 安全边界 | 明确非 Claude Code 下哪些能力只是软约束。 |

### 5.2 不在范围内

- 不把 Claude Code hooks 改成通用 hook 框架。
- 不内嵌完整交互式 AI 终端。
- 不为每个第三方工具写深度插件。
- 不引入 Web 服务或额外依赖。
- 不承诺非 Claude Code 可以自动拦截危险命令。

### 5.3 可量化验收

| # | 项 | 标准 | 验证方式 |
|---|---|---|---|
| V1 | 文档可读 | 3 分钟内能回答“非 Claude Code 下怎么用” | 人工读 README/MAINTENANCE/本任务文档 |
| V2 | 能力边界清楚 | 每个关键能力标注“通用 / Claude 专属 / 软约束” | 检查能力矩阵 |
| V3 | 后续 CLI 可落地 | `export-context` 输入/输出和安全边界明确 | 读 DESIGN §3 |
| V4 | 不破坏现有链路 | 现有 doctor/smoke/check_health 继续通过 | 运行维护脚本 |

## 6. 风险与回滚

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 抽象层变成新杂物 | 中 | 维护成本上升 | 先只做文档和上下文导出，不做大框架 |
| 用户误以为非 Claude Code 也有硬拦截 | 高 | 安全感虚高 | 文档明确“软约束”和“不可等效” |
| Adapter 漂移 | 中 | 不同环境说明不一致 | 能力矩阵进 manifest，后续用脚本检查 |
| Claude Code 体验被稀释 | 低 | 原有自动化变弱 | 保留 Claude Code 专属路径，不为通用牺牲现有 hooks |

回滚预案：

- L1：如果上下文导出设计不合适，只保留文档说明，不实现 CLI。
- L2：如果 adapter 维护成本太高，只保留 `generic` fallback。
- L3：如果通用化方向失败，删除 compatibility 文档，不影响现有 Claude Code runtime。
